## 1. Migraciones Alembic como fuente de verdad del esquema

El punto que más pesaba: ayer se dejó anotado que Postgres se bootstrapeaba
con `Base.metadata.create_all` más un `alembic stamp head` para hacer catch-up,
y que la situación era frágil. Investigando resultó ser peor de lo que
pensábamos: la migración "inicial" (`608f62c5ca65`) era un retrofit que solo
añadía una columna sobre un esquema que asumía ya existente, y **las tablas
`tenants` y `users` nunca tuvieron migración** — solo se creaban vía
`create_all`. Como la migración posterior `f7c9d2b85a43` (invitaciones)
declara FKs a `tenants.id` y `users.id`, un `alembic upgrade head` sobre una
BD vacía reventaba. Por pura suerte nadie había intentado ese flujo en limpio
desde que se hizo la separación web.

### Arreglo

- **Reescrita `608f62c5ca65_initial_schema.py`** para crear el esquema
  pre-web completo (applications, batches, pages, barcodes, templates,
  operation_history) en lugar de solo añadir una columna. La revisión ID se
  mantiene, así que los despliegues ya migrados (con `alembic_version` en
  `f7c9d2b85a43`) siguen siendo no-ops.
- **Nueva migración `bf8a2c4d1e9a_add_tenants_and_users.py`**, insertada en
  el chain entre `bd2be614cf0f` y `e5b7c3d94f10`. Es **idempotente** — usa
  `inspect(op.get_bind())` para no recrear tablas si ya existen, de modo que
  despliegues previos (donde `create_all` ya las creó) no se rompen.
- **Simplificado `docker-bootstrap-db.py`** a un único `alembic upgrade head`.
  Las migraciones son ahora la fuente única de verdad; el contenedor ya no
  hace `create_all` por su cuenta.

### Tests

Dos tests nuevos en `tests/test_migrations.py`:
- `alembic upgrade head` sobre una BD SQLite vacía produce un esquema
  equivalente al de `Base.metadata.create_all` (compara columnas, tipos,
  índices, unique constraints y FKs tabla por tabla).
- El historial de migraciones tiene un único head (evita ramas sin resolver).

Sin este test cualquier futuro agujero como el de `tenants`/`users` volvería
a pasar desapercibido hasta el primer despliegue limpio en producción.

Commit: **`f172df6 fix: migraciones Alembic como fuente de verdad del esquema`**

## 2. Toasts en UI al completar o fallar el pipeline

Ayer se introdujo el WebSocket de progreso del pipeline, pero al terminar
la UI solo refrescaba en silencio: nada en pantalla confirmaba al usuario
que la operación había terminado (ni éxito ni error). Se ha añadido un
sistema de **toasts minimalista, sin dependencias nuevas**.

- `useToast.ts` — composable con `success`/`error`/`info`, timeout
  cancelable (si el usuario descarta manualmente, el setTimeout se cancela
  en vez de acumularse).
- `ToastContainer.vue` — stack fijo abajo-derecha con `TransitionGroup`,
  paleta Catppuccin Latte y animación slide-in.
- Se monta en `App.vue` y se dispara desde `BatchDetailView.vue` al recibir:
  - `pipeline_completed` con `any_error=true` → `toast.error` ("completado
    con errores, revisa las páginas marcadas").
  - `pipeline_completed` limpio → `toast.success`.
  - `pipeline_error` → `toast.error` con el mensaje del backend.

De paso se **paralelizan con `Promise.all` los 3 fetches** que se disparan
al completar el pipeline (`fetchOne`, `fetchPages`, `fetchPage`), antes eran
secuenciales.

Tras una pasada de code review interna (3 agents en paralelo) se aplicaron
tres fixes: tipar `kindStyles`/`kindIcons` como `Record<ToastKind, string>`,
cancelar timers en el `dismiss` y la paralelización ya mencionada.

Commit: **`4bb936e feat: toasts en UI al completar o fallar pipeline`**

## 3. Paginación en los listados de la API

Cuatro endpoints (`/api/applications`, `/api/batches`, `/api/users`,
`/api/invitations`) devolvían todo lo del tenant sin límite. Se ha añadido
paginación preventiva antes de que duela.

### Cambios de contrato

| Endpoint | Query params nuevos | Respuesta |
|---|---|---|
| `GET /api/applications` | `?limit=50&offset=0` (límite max 200) | `{items, total, limit, offset}` |
| `GET /api/batches` | `?limit&offset` (+ los filtros existentes) | idem |
| `GET /api/users` | `?limit&offset` | idem |
| `GET /api/invitations` | `?limit&offset` | idem |

Es un cambio **breaking** (antes devolvían `list[T]` raw, ahora un
wrapper `PaginatedResponse[T]`), pero la API está aún en MVP y solo el
frontend propio la consume.

### Detalles de implementación

- Schema genérico `PaginatedResponse[T]` + dependency `pagination_params`
  con validación FastAPI `Query(ge=1, le=200)` para `limit` y `Query(ge=0)`
  para `offset`.
- Los endpoints hacen un `SELECT count()` sobre la subquery filtrada antes
  de aplicar `limit/offset`, de modo que `total` respeta `application_id`,
  `state`, etc. — no es un total "global".
- Frontend: tipo `Paginated<T>` compartido, stores (`applications.ts`,
  `batches.ts`) desempaquetan `.items` y exponen `total`. TeamView desempaqueta
  también.

### Tests

4 tests nuevos en `TestPagination`:
- `limit`/`offset` funcionan (total=7, paginación en 3 fragmentos).
- `limit=0`, `limit=201` y `offset=-1` devuelven **422**.
- `total` refleja el filtro, no el global del tenant.
- Caso básico en `/api/applications`.

Existentes actualizados (9 tests) para desempaquetar `.items`/`.total` en
las aserciones.

Commit: **`7b6bbf2 feat: paginación en listados de la API web`**

## Decisiones tomadas

- **Migración `bf8a2c4d1e9a` idempotente** en vez de limpia: permite
  meterla en el chain sin romper despliegues previos (staging/dev) donde
  `tenants`/`users` ya existen vía `create_all`. Coste: un `inspect()`
  extra al arrancar; beneficio: no hay que intervenir manualmente los
  entornos existentes.
- **Mantener revisión ID `608f62c5ca65`** al reescribir la initial en
  lugar de crear una nueva: los despliegues con `alembic_version` stampado
  ahí o más adelante siguen siendo no-ops. Una initial nueva habría
  requerido re-stampar manualmente.
- **Toasts sin librería externa**: `@vueuse/core` no aporta y añadir
  `sonner` / similar era desproporcionado para tres call-sites. ~60
  líneas de código total.
- **Wrapper `{items, total, limit, offset}` en la respuesta** en vez de
  usar headers `X-Total-Count`: es más ergonómico desde JS, más auto-
  documentado en el schema, y coherente con cómo ya consume datos el
  frontend. Coste: breaking change puntual.
- **No tocar UI de paginación todavía**: el frontend devuelve los
  primeros 50 items y ya. Cuando un tenant pase de 50 aplicaciones/lotes
  añadiremos "Cargar más" o paginador clásico — no antes.
