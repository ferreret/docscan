# Progreso 2026-04-16 — Brainstorming y plan del editor de pipeline en web

## Resumen

Sesión corta en la rama `feature/web` dedicada a **planificación**, no a
implementación de código. El MVP web está validado manualmente (sesión
anterior), y la conclusión compartida es que el hueco funcional más
importante antes de seguir pulido es el **editor de pipeline en web**: sin
él, la versión web no es un producto autónomo porque el cliente necesita
abrir el configurador de escritorio para dejar operativa cada aplicación.

Esta sesión traduce ese objetivo en dos documentos accionables:
**spec de diseño** y **plan de implementación paso a paso**, ambos
commiteados. Se decidió **posponer** el envío automático de invitaciones
por email (no bloquea funcionalidad) y **priorizar** el editor de pipeline.
La implementación empezará en la próxima sesión.

## 1. Reorientación de prioridades

Al revisar la lista de pendientes se identificó que, de los cinco puntos
abiertos tras la prueba manual del MVP (envío de emails, CI de migraciones,
rate limiting, escenarios manuales, decisión sobre el editor de pipeline),
solo uno era un **hueco funcional real**: el editor de pipeline. El resto
era pulido o hardening.

Se confirmó el objetivo de proyecto — alcanzar **paridad funcional con la
versión de escritorio** en el frontend web — y se acordó que la estrategia
más razonable es **dividir en sub-proyectos** porque la pestaña Pipeline
del configurador desktop es parte de un conjunto de seis pestañas, y
abordarlo todo de golpe es sobredimensionado. Los sub-proyectos quedan en
este orden:

1. Editor de Pipeline *(este sub-proyecto)*
2. Pestaña Imagen
3. Pestaña Eventos
4. Pestaña Campos de lote
5. Pestaña Transferencia
6. Pestaña General

Cada uno tendrá su propia spec + plan + ciclo de implementación.

## 2. Brainstorming guiado del Editor de Pipeline

Se ejecutó el skill de brainstorming con seis preguntas clarificadoras,
cuatro de ellas apoyadas en maquetas visuales. Las decisiones cerradas en
esta sesión son:

| Punto | Decisión |
|---|---|
| **Fases de entrega** | Incremental por tipo de step: v1 Barcode → v2 ImageOp → v3 OCR → v4 Script. El más complejo (ScriptStep, con editor de código) se deja al final. |
| **Ubicación en el frontend** | Página dedicada `/applications/:id/pipeline` (URL compartible, pantalla propia). |
| **Representación de la lista** | Rows compactas con drag-to-reorder (estilo tabla, como el configurador desktop; escala bien a pipelines de 10-20 steps). |
| **Mecánica de edición** | Drawer lateral derecho (patrón SaaS moderno; deja la lista visible y acoge el futuro editor de código del ScriptStep). |
| **Guardado** | Save explícito por step (drawer con draft local; drag sí persiste inmediato). |
| **Endpoint backend** | `PUT /api/applications/:id/pipeline` que reemplaza el pipeline completo. |

Una decisión técnica importante: la **validación del pipeline no se
duplica** en el backend web. Se reutiliza `app/pipeline/serializer.deserialize()`
(la misma función que usa el runner). Así, un pipeline que valida en el
editor está garantizado de ser ejecutable por el runner.

También se comprobó en el código que editar el pipeline **no afecta a
batches en ejecución**: el `PipelineExecutor` se construye al arrancar el
batch (`web/api/tasks/pipeline_runner.py:158`), con los steps ya en memoria,
así que ediciones posteriores al `pipeline_json` solo afectan a batches
futuros.

## 3. Plan de implementación paso a paso

Sobre la base de la spec, se escribió un plan de 14 tasks con pasos
bite-sized (TDD + commits independientes) para el alcance v1:

- **Backend (Tasks 1-5):** dos endpoints nuevos (`GET` y `PUT`), 12 tests
  nuevos en `test_web_api.py`, validación delegada a `deserialize()`.
- **Frontend (Tasks 6-12):** tipos TS, API wrapper, **Pinia store con 8
  tests unitarios** (se introduce vitest por primera vez en el frontend),
  ruta nueva, botón en la vista de aplicación, componentes
  `PipelineStepList` + `PipelineStepRow` con drag-to-reorder
  (`vue-draggable-plus`), `PipelineStepDrawer`, `AddStepMenu` y el
  `BarcodeStepForm` con todos los campos del dataclass.
- **Validación (Task 13):** prueba manual end-to-end guiada (flujo
  completo, errores, aislamiento multi-tenant, ejecución real de un lote
  con el pipeline configurado desde la web) y suite completa de tests.
- **Cierre (Task 14):** informe de progreso + push + memoria.

Un punto que merece mencionarse: en el self-review del plan se detectó un
bug de arquitectura latente en `BarcodeStepForm.vue` (patrón doble watcher
prop↔local draft que causaría un bucle infinito en Vue 3) y se corrigió
antes de cerrar el plan. El form es ahora **fully-controlled**: recibe
`modelValue`, emite `update:modelValue` con el step completo actualizado,
sin estado local propio.

Commit: **`eb80530 docs: plan de implementacion v1 editor de pipeline (BarcodeStep)`**

## Decisiones tomadas

- **Posponer el envío automático de invitaciones**: no bloquea funcionalidad;
  hoy el admin comparte el link manualmente desde la UI y eso cubre el
  onboarding básico. Se retomará tras v1 del editor de pipeline.
- **Dividir el editor de pipeline por tipo de step**: cada iteración
  (barcode → image_op → ocr → script) es deployable y útil por sí misma.
  Evita una entrega única gigante y permite cortar feedback antes.
- **Página dedicada para el editor en lugar de pestaña o modal**: el editor
  es lo bastante complejo como para merecer su propia URL. Además, una URL
  compartible ayuda al admin a redirigir a un compañero.
- **Save explícito por step en lugar de auto-save**: más predecible, permite
  cancelar desde el drawer, y encaja con el estándar de editores SaaS
  (Airtable, Retool). El auto-save granular se descartó porque un pipeline
  se consume entero por el runner y no hay beneficio de persistencia
  parcial.
- **Único PUT con el pipeline completo en lugar de CRUD granular por step**:
  el `pipeline_json` se almacena como TEXT, tratarlo como agregado es
  coherente con cómo lo consume el resto del sistema. Evita parse/modify/
  serialize y la complejidad de coordinación entre endpoints.
- **Introducir vitest en el frontend como parte de v1**: hasta ahora el
  frontend no tenía tests unitarios. El editor de pipeline tiene lógica
  suficiente en el store (add/update/remove/reorder/save/fetch) como para
  justificar la infraestructura, que además servirá al resto del proyecto.
- **Reutilizar `deserialize()` para validación**: una sola fuente de verdad
  para qué es un pipeline válido. Evita que un pipeline valide en el editor
  pero falle en el runner por divergencia de reglas.
