# Progreso 2026-04-09 — API web: del CRUD básico al MVP funcional desplegable

## Resumen

Sesión larga e intensa que ha cerrado el MVP funcional de la API web SaaS
**y ha dejado el stack completo listo para desplegar con un solo comando**.
Sobre la base publicada el 2026-04-07 (FastAPI + JWT + CRUD de aplicaciones)
se han añadido **ocho piezas encadenadas**: CRUD de lotes, upload de páginas
con storage en disco, un fix importante de limpieza encontrado en un smoke
test end-to-end contra PostgreSQL real, un bloque de automatizaciones de
Claude Code (hooks, skills, subagents), configuración de dos MCP servers
nuevos sin filtrar credenciales, la ejecución del pipeline como background
task de FastAPI, un `docker-compose.yml` con los 4 servicios del stack
(Postgres + MinIO + Redis + API) listo para arrancar con un solo comando,
y finalmente un fix de seguridad para eliminar credenciales de ejemplo que
GitGuardian detectó en el commit del compose. Todo sobre la rama
`feature/web`, con tests integrados antes de cada commit.

La API pasa de ser "un CRUD de recursos" a ser "una plataforma que procesa
documentos": un cliente puede registrarse, crear una aplicación con un
pipeline definido en JSON, crear un lote, subir imágenes o PDFs, lanzar el
pipeline y recuperar los resultados (OCR, barcodes, campos, flags) a través
de los endpoints REST. Y cualquiera que clone el repo puede levantar el
stack completo con `docker compose up --build` — sin instalar Python,
PostgreSQL ni ninguna otra dependencia en su máquina más allá de Docker.

## 1. CRUD de lotes

Se han añadido los endpoints REST para gestionar los lotes de cada tenant,
con el mismo patrón tenant-scoped que ya se usaba en aplicaciones.

### Endpoints nuevos

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/batches` | Lista con filtros opcionales `?application_id=` y `?state=` |
| `POST` | `/api/batches` | Crea un lote validando que la aplicación pertenece al tenant |
| `GET` | `/api/batches/{id}` | Obtiene un lote por ID |
| `PATCH` | `/api/batches/{id}` | Actualiza estado, `page_count`, paths, etc. |
| `DELETE` | `/api/batches/{id}` | Elimina en cascada páginas, historial y ficheros |

### Puntos de control implementados

- **Validación del estado**: en el PATCH, se rechaza con HTTP 422 cualquier
  valor que no esté en `BATCH_STATES` (`created`, `read`, `verified`,
  `ready_to_export`, `exported`, `error_read`, `error_export`).
- **Aislamiento de tenants**: un tenant no puede listar, leer, modificar ni
  crear lotes dentro de aplicaciones que no sean suyas (HTTP 404 en cualquiera
  de esos casos).
- **Filtros combinables**: se pueden usar `application_id` y `state` a la vez.

### Tests

13 tests nuevos cubriendo: crear, listar, filtros por aplicación/estado,
obtener, actualizar (estado válido e inválido), eliminar, aislamiento de
tenants en ambos sentidos y acceso sin autenticación.

Commit: **`3c02af6 feat: batches CRUD — tenant-scoped REST endpoints`**

## 2. Upload de páginas

Se ha construido todo el flujo para que los clientes puedan subir, listar,
descargar y eliminar páginas dentro de un lote.

### Storage

Se ha creado un servicio de almacenamiento desacoplado del router
(`web/api/storage.py`) basado en filesystem, con una API pensada para migrar
después a MinIO/S3 sin tocar el código de los endpoints.

- **Layout en disco**: `{base_path}/{tenant_id}/{batch_id}/{uuid}.{ext}`
- **Métodos**: `save`, `read`, `delete`, `exists`, `absolute_path`
- **Configuración**: nuevas variables `DOCSCAN_WEB_STORAGE__BASE_PATH`
  (default `/tmp/docscan-storage`) y `DOCSCAN_WEB_STORAGE__PDF_DPI`
  (default 200).

La dependencia se inyecta via `StorageDep` (Depends estándar de FastAPI),
lo que permite sobreescribirla en tests con `tmp_path`.

### Endpoints nuevos

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/api/batches/{batch_id}/pages` | Upload multipart de uno o más ficheros |
| `GET` | `/api/batches/{batch_id}/pages` | Lista las páginas del lote |
| `GET` | `/api/batches/{batch_id}/pages/{page_id}` | Metadatos de una página |
| `GET` | `/api/batches/{batch_id}/pages/{page_id}/image` | Descarga del binario |
| `DELETE` | `/api/batches/{batch_id}/pages/{page_id}` | Borra página + fichero |

### Lógica del upload

- **Imágenes individuales** (`jpg`, `jpeg`, `png`, `bmp`, `tif`, `tiff`): se
  guardan tal cual, sin decodificar, creando una `Page` por cada fichero.
- **PDFs**: se abren con `pymupdf` desde memoria, cada página se renderiza a
  PNG (a la DPI configurada) y se guarda como una `Page` independiente. Un
  PDF de 10 páginas → 10 registros `Page` con `page_index` consecutivos.
  Tras la revisión de eficiencia, el split se hace **página a página como
  generador** para no mantener todas las imágenes PNG en memoria al mismo
  tiempo.
- **`page_index` incremental**: se calcula el máximo existente en el lote y
  se empieza a partir del siguiente, permitiendo uploads parciales sin
  conflictos.
- **`batch.page_count` automático**: se recalcula al subir y al borrar
  páginas.
- **Download vía `FileResponse`**: streaming eficiente sin cargar todo el
  fichero en memoria.
- **Validaciones de entrada**: extensión soportada, fichero no vacío, PDF
  válido (en caso contrario HTTP 400).

### Tests

15 tests nuevos repartidos en dos clases (`TestPagesUpload` y `TestPagesRead`)
cubriendo: upload simple, múltiples ficheros en una llamada, PDF multipágina,
formato no soportado, PDF corrupto, fichero vacío, `page_index` incremental,
lote inexistente, lote de otro tenant, listado, metadatos, descarga (con
verificación de magic bytes del PNG), borrado con actualización de
`page_count`, aislamiento de tenant y acceso sin autenticación.

Commit: **`043e49d feat: pages upload — multipart endpoints con storage filesystem`**

## 3. Smoke test end-to-end + fix crítico de cleanup

Tras completar las dos piezas anteriores se ejecutó un **smoke test completo
contra PostgreSQL real** (docker `docscan-pg`) con curl en vez de tests
in-proceso. El flujo fue: registro → login → crear aplicación → crear lote
→ subir PDF de 3 páginas → listar → descargar imagen → borrar página → borrar
lote → borrar aplicación → cleanup. El flujo funcionó por completo, pero al
inspeccionar el directorio de storage tras el cleanup final aparecieron
**ficheros huérfanos**: los PNGs de las páginas 2 y 3 del PDF seguían en
disco.

### Diagnóstico

Cuando se borra un `Batch` (o una `Application`) via la API, la cascada del
ORM elimina correctamente los registros `Page` de la base de datos, pero los
ficheros en disco quedan abandonados. El `delete_page` individual sí borraba
su fichero porque llamaba explícitamente a `storage.delete`, pero la cascada
a nivel de batch/aplicación no tenía forma de conocer los paths.

### Fix

`delete_batch` y `delete_application` ahora recogen los `image_path` **antes**
del `db.delete(parent)`, hacen el commit, y tras él iteran los paths llamando
a `storage.delete` para cada uno. Para aplicaciones la recolección es doble
(`for batch in app.batches for page in batch.pages`).

### Tests

2 tests nuevos (`TestPagesStorageCleanup`) que asertan que el directorio de
storage queda vacío tras ambos deletes, incluyendo casos con PDFs multipágina
que generan varios ficheros. La fixture de test se refactorizó para exponer
`storage_dir` como fixture propia que permite inspeccionar el filesystem.

### Verificación en vivo

Se re-ejecutó el smoke test contra PostgreSQL: 3 ficheros antes del
`DELETE /batches/{id}` → 0 después. Confirmado el fix.

Commit: **`e72432d fix: delete_batch/application limpia ficheros de storage huérfanos`**

## 4. Automatizaciones de Claude Code

Antes de continuar con más producto se dedicó un bloque a **mejorar la
herramienta de trabajo**. Se ejecutó la skill `claude-automation-recommender`
sobre el proyecto y se identificaron los cinco tipos de automatización más
útiles. Todos los propuestos se han implementado.

### Hooks (dos scripts nuevos)

Funcionan a nivel de Claude Code: se ejecutan automáticamente antes y
después de cada operación de edición de ficheros, sin necesidad de
intervención manual.

- **`.claude/hooks/ruff-format.sh`** (PostToolUse): al guardar o editar un
  fichero `.py`, ejecuta `ruff format` y `ruff check --fix` automáticamente.
  Usa el binario del `.venv` del proyecto si existe. Resultado: todo el
  código Python que se va tocando queda formateado y con imports limpios
  sin que nadie se acuerde de lanzar el linter.
- **`.claude/hooks/block-protected.sh`** (PreToolUse): rechaza cualquier
  intento de editar `.env`, `.env.*` o `secrets.enc`. Es una red de
  contención contra incidentes como el del commit `16f7f2d` (GitGuardian).

Ambos verificados en vivo durante la sesión: ruff reformateó un fichero
Python mal formateado justo tras el `Write`, y el hook de bloqueo rechazó
con el mensaje custom un intento de escribir a `/tmp/.env`.

### Skills (dos paquetes nuevos)

- **`web-api-patterns`**: cristaliza las convenciones de la API web
  (tenant scoping, helpers en `_helpers.py`, storage cleanup al borrar,
  schemas Pydantic, tests, no usar `print`). Es la documentación viva
  del patrón que estamos siguiendo, ya incorporando las lecciones del
  fix de hoy.
- **`progreso-doc`**: template + procedimiento para generar este mismo
  informe diario. Define el tono narrativo para el jefe, la estructura
  de secciones, y el flujo de commit. El informe que estás leyendo es
  una aplicación de este template.

### Subagents (dos agentes nuevos)

- **`security-reviewer`**: auditor especializado en aislamiento multi-tenant.
  Su checklist se enfoca en detectar queries sin filtro de `tenant_id`, FKs
  cruzadas sin validar, 404 vs 403, fugas en mensajes de error. Pensado
  para invocarse tras cualquier cambio en `web/api/routers/`.
- **`frontend-scaffolder`**: scaffolder Vue 3 + Vite + Tailwind + Pinia,
  preparado para cuando llegue el paso del frontend (ahora paso 5 del
  roadmap). Conoce el stack decidido, la estructura esperada y cómo
  consumir la API REST existente.

### MCP servers nuevos (con un fix de credenciales)

Se añadieron dos servidores MCP al `.mcp.json` del proyecto para que
funcionen automáticamente tras reiniciar la sesión de Claude Code:

- **PostgreSQL MCP**: permite consultar la base de datos de desarrollo
  directamente sin montar un ciclo de `uvicorn + curl`. Útil para verificar
  estado de migraciones, inspeccionar tablas o probar queries.
- **Playwright MCP**: preparado para el paso del frontend — permitirá
  automatizar pruebas de navegador contra la UI Vue 3 cuando llegue.

El primer intento de registrar PostgreSQL metió la URL de conexión de
desarrollo (con contraseña en texto plano) directamente en `.mcp.json`,
que es un fichero tracked. Eso hubiese disparado GitGuardian de nuevo.
El fix
fue un **wrapper bash** (`.claude/scripts/mcp-postgres.sh`) que lee la
URL del `.env` (que sí está en `.gitignore`) y le quita el prefijo
`+psycopg` antes de invocar el servidor MCP. Resultado: el repo no
contiene credenciales en ningún momento y cualquiera que clone el repo
solo necesita tener su propio `.env`.

## 5. Ejecución del pipeline como background task

La pieza que cierra el MVP funcional. La API ahora ya no es solo un CRUD
de recursos: **es una plataforma que procesa documentos**.

### Nuevo endpoint

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/api/batches/{id}/run` | Dispara la ejecución del pipeline sobre todas las páginas del lote. Devuelve 202 Accepted inmediato. Rechaza con 409 si el lote no tiene páginas. |

### Cómo funciona

El endpoint es un disparador muy ligero: valida que el lote pertenece al
tenant, que tiene al menos una página y delega la ejecución real a un
**`BackgroundTask` de FastAPI**. El cliente recibe el 202 en milisegundos
y puede hacer polling a `GET /api/batches/{id}` para ver cómo el estado
transiciona de `created` a `read` (éxito) o `error_read` (fallo a nivel
de lote).

El trabajo real está en `web/api/tasks/pipeline_runner.py`, un módulo
síncrono que:

1. Abre su **propia session** de base de datos (las sessions del request
   están ya cerradas cuando corre el background task).
2. Carga el `Application` y deserializa su `pipeline_json` usando el
   serializer del desktop.
3. Construye un `PipelineExecutor` **reutilizando íntegramente la clase
   del desktop** — gracias a que las dataclasses `PageContext`,
   `BatchContext` y `AppContext` ya estaban extraídas (trabajo de la
   sesión 2026-04-07), el executor es duck-typed y no necesita ninguna
   adaptación.
4. Recorre todas las páginas del lote: para cada una carga la imagen
   desde el storage (`cv2.imread`), construye un `PageContext`, ejecuta
   el pipeline y persiste los resultados de vuelta al modelo ORM `Page`:
   `ocr_text`, `index_fields_json`, `needs_review`, `review_reason`,
   `processing_errors_json`, `script_errors_json`, `pipeline_processed`,
   y los `barcodes` detectados.
5. Si el executor no se puede construir (pipeline JSON con tipo
   desconocido, script con error de compilación, etc.), el lote queda
   en `error_read`. Si falla una página concreta pero el resto se
   procesa, el error se acumula en `page.processing_errors_json` y el
   lote queda en `error_read`.

### Tests

8 tests nuevos (`TestPipelineRun`) cubriendo:

- Pipeline vacío marca el lote como `read`
- `ScriptStep` que escribe en `page.fields` y `page.ocr_text` → verificación
  de que los resultados se persisten en la base de datos
- `ScriptStep` que marca `needs_review=True` → verificación de que el flag
  llega al modelo ORM
- Lote vacío rechazado con 409
- Lote inexistente → 404
- Lote de otro tenant → 404
- Pipeline JSON con tipo de paso desconocido → lote en `error_read`
- Acceso sin autenticación → 401

Los tests usan `ScriptStep` deliberadamente (no OCR ni barcodes reales)
para no depender de motores externos y ser rápidos y deterministas.

Commit: **`d89cbca feat: pipeline execution as background task`**

## 6. Docker Compose: stack completo de desarrollo

Con el MVP funcional cerrado, el siguiente paso natural era facilitar el
despliegue local. Hasta esta sesión, para probar la API había que tener
Python 3.14, todas las dependencias nativas (opencv, pyzbar, zxing-cpp,
rapidocr, pymupdf), y un PostgreSQL corriendo en la máquina host. Con el
nuevo `docker-compose.yml`, basta con tener Docker y ejecutar
`docker compose up --build`.

### Servicios del stack

| Servicio | Imagen | Propósito |
|---|---|---|
| `db` | `postgres:16-alpine` | Base de datos persistente |
| `minio` | `minio/minio:latest` | Storage S3-compatible (listo para migrar desde el filesystem) |
| `redis` | `redis:7-alpine` | Cola para futuros background tasks con ARQ |
| `api` | Construida desde `Dockerfile.web` | La API REST FastAPI |

Todos con healthchecks, volúmenes persistentes (`db_data`, `minio_data`,
`api_storage`), y dependencias encadenadas (`depends_on` con
`condition: service_healthy`) para que el API no arranque hasta que
Postgres esté listo.

### Dockerfile.web

La imagen parte de `python:3.14-slim-bookworm` y añade solo las
dependencias de sistema imprescindibles: `libzbar0` (pyzbar), `libgl1` y
`libglib2.0-0` (opencv). Las dependencias Python vienen de
`requirements.txt` + `requirements-web.txt`, filtrando **al vuelo**
`PySide6` y `python-sane` (dependencias del desktop que no aportan nada
en el contenedor y pesarían ~500MB extra). La imagen final ronda los
3 GB — lo habitual para un stack con opencv, rapidocr y onnxruntime.

### Bootstrap de la BD

El proyecto original creaba las tablas con `Base.metadata.create_all()`
al arrancar el desktop, y Alembic solo manejaba los cambios evolutivos
desde ese punto. Contra un PostgreSQL fresco, esto provoca un problema:
la primera migración Alembic asume que las tablas existen y falla
intentando hacer `ALTER TABLE applications`.

La solución es `docker-bootstrap-db.py`, un script de inicialización que
se ejecuta antes del `uvicorn`:

1. Se conecta a la BD usando `DOCSCAN_WEB_DATABASE__URL` del entorno.
2. Comprueba si existe la tabla `alembic_version`.
3. **Si no existe** (BD fresca): ejecuta `Base.metadata.create_all()`
   para crear todas las tablas de golpe, y luego `alembic stamp head`
   para marcar todas las migraciones como aplicadas sin ejecutarlas.
4. **Si existe**: ejecuta `alembic upgrade head` normalmente para
   aplicar cualquier migración pendiente.

Este enfoque permite que el mismo contenedor funcione tanto en una
instalación nueva como en una actualización futura.

### Obstáculos resueltos durante la construcción

El build de la imagen descubrió varios problemas que llevaba arrastrando
el proyecto sin darse cuenta:

- `psycopg[binary]==3.2.9` pinneado en `requirements-web.txt` pero no
  tiene wheel para Python 3.14 — bumpeado a `3.3.3` (la versión que
  realmente estaba en el `.venv` local).
- `pydantic[email]==2.11.7` por el mismo motivo — bumpeado a `2.12.5`.
- `python-multipart` faltaba en los requirements pese a que FastAPI lo
  necesita para procesar los uploads de páginas. Estaba en el `.venv`
  local por ser dependencia transitiva de algo, pero no declarado.
- El módulo `config/` del proyecto no se copiaba en la imagen.
- `alembic/env.py` leía la URL de la BD hardcoded del settings del
  desktop — ahora comprueba `DOCSCAN_WEB_DATABASE__URL` primero.
- Error de permisos al escribir en el volumen `api_storage`: el
  contenedor corre como usuario `docscan` (uid 1000) pero el mount point
  lo crea Docker como `root`. El fix: crear el directorio en el
  `Dockerfile` y hacer `chown` antes del `USER` instruction, así el
  mount hereda los permisos.

Cada uno de estos se fue descubriendo iterativamente durante el build, y
en conjunto han dejado el `requirements-web.txt` y la configuración
mucho más consistentes con lo que realmente funciona.

### Documentación

Se ha creado `docs/deploy.md` con instrucciones paso a paso para el
arranque, una tabla de servicios y puertos expuestos, un ejemplo de
verificación con curl, los comandos útiles de docker compose y una

## 7. Incidente GitGuardian: credenciales de ejemplo en el repo

Poco después de pushear el commit del compose, GitGuardian alertó sobre
**4 secretos** detectados en el commit `96a5fd0`. Los strings problemáticos
eran los valores por defecto `docscan` y `docscan123` que se habían dejado
como fallback en `docker-compose.yml`, `web/.env.example` y `docs/deploy.md`.

Aunque eran credenciales de desarrollo sin ningún valor real, el patrón
viola dos principios:

1. **Cualquier string que LUZCA como una contraseña dispara las herramientas
   de escaneo automático**, independientemente de su uso real.
2. **Alguien podría arrancar el stack en producción sin cambiar los
   defaults**, dando a un atacante un punto de entrada trivial.

Es el segundo incidente similar de la rama (el primero fue `16f7f2d` con
credenciales de PostgreSQL hardcoded en `config/settings.py`). La lección
se consolida: ningún string con pinta de credencial debe quedar en el
repo, ni como ejemplo, ni como fallback.

### Fix aplicado

- **`docker-compose.yml`**: todas las variables de credenciales usan ahora
  la sintaxis `${VAR:?mensaje}` en lugar de `${VAR:-default}`. Si alguna
  no está definida en el `.env` local, `docker compose up` **se niega a
  arrancar** con un error claro apuntando al nombre de la variable. Cero
  defaults predecibles.
- **`web/.env.example`**: todos los campos sensibles llevan ahora un
  placeholder explícito `CHANGE_ME_xxx` que el usuario tiene que
  reemplazar antes de arrancar. Incluye comentarios explicando qué
  generar y cómo.
- **`docs/deploy.md`**: la tabla de servicios ya no muestra credenciales
  de ejemplo — las referencia al `.env` local. Los ejemplos de curl
  usan variables `$EMAIL` / `$PASSWORD` en lugar de valores literales.
- **`Dockerfile.web`**: `chown docscan:docscan` → `chown 1000:1000` y
  `USER docscan` → `USER 1000:1000`. La forma `user:group` en texto
  podía confundir a GitGuardian con un patrón `user:password`; la forma
  numérica elimina la ambigüedad.
- **Este mismo informe de progreso**: eliminada la mención textual a
  `postgresql://docscan:docscan@...` que existía en la narrativa del
  incidente anterior.

### Sobre el historial de git

El commit `96a5fd0` sigue existiendo en el historial con los strings
originales. Para eliminarlos por completo habría que reescribir el
historial con `force push`, una operación destructiva que cambia los
hashes de todos los commits posteriores y rompe las referencias de
cualquier clon que ya exista. **No se ha hecho**: como son valores de
ejemplo sin uso real, el fix forward es suficiente y replica el patrón
del incidente anterior (`16f7f2d`). GitGuardian, al ver el nuevo commit
que elimina los strings del estado actual del repo, marca la alerta
como resuelta en su panel.

Commit: **`f36ee77 fix: remove hardcoded dev passwords — GitGuardian incident 96a5fd0`**

## Decisiones tomadas

- **`BackgroundTasks` de FastAPI en vez de ARQ + Redis**: para el MVP
  es más que suficiente y no requiere desplegar Redis. ARQ se añade
  cuando haga falta horizontal scaling o las ejecuciones se vuelvan
  demasiado largas. Redis ya está levantado en el compose para cuando
  llegue el momento.
- **Reutilización del `PipelineExecutor` desktop sin tocarlo**: gracias
  a la extracción previa de `page_context.py` y al diseño duck-typed
  del executor, todo el código de pipeline se reusa sin modificaciones.
  Esto valida el esfuerzo de la sesión 2026-04-07.
- **Storage cleanup explícito en routers, no via SQLAlchemy events**:
  más visible, más testeable, más fácil de razonar que un event listener
  global.
- **Credenciales fuera del repo por defecto**: el patrón del wrapper
  bash para MCPs servirá como referencia para cualquier credencial
  futura. Ningún secreto debe acabar en ficheros tracked.
- **Hooks en `.claude/settings.json` (tracked), no en `.local.json`**:
  así cualquiera que clone el repo hereda los hooks automáticamente
  y no depende de cada desarrollador reconfigurar los suyos.
- **Compose sin defaults de credenciales**: `${VAR:?mensaje}` en vez de
  `${VAR:-default}`. Si el usuario no define una variable sensible, el
  stack se niega a arrancar con un error claro — mejor fallar en el
  arranque que en producción con una contraseña predecible.
- **Bootstrap de BD con `create_all` + `alembic stamp head` en BD fresca**:
  soluciona la limitación de que las migraciones del proyecto asumen
  tablas preexistentes (creadas por el desktop con `create_all`). Mismo
  script funciona para BD fresca y para BD con migraciones pendientes.
- **Credenciales de infraestructura del compose siempre en `.env` local**:
  ni siquiera como valor por defecto del YAML. Segundo incidente
  GitGuardian en la rama ha consolidado esta norma.
