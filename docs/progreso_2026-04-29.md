# Progreso 2026-04-29 — Migración del backend web a ARQ (cola de tareas)

## Resumen

Sesión partida en dos bloques. Por la mañana se cerraron tres mejoras finales
del frontend web (badge unificado de estado de lote, manejo cross-tenant de
404, auto-refresh del listado mientras hay lotes activos). Por la tarde se
abordó el cambio de infraestructura más sustancial pendiente en la rama
`feature/web`: sustituir las `BackgroundTasks` de FastAPI por una cola de
tareas dedicada (ARQ + Redis + worker independiente), de modo que el pipeline
y la transferencia ya no compitan por threads del proceso del API y los lotes
no queden colgados en `running`/`transferring` al reiniciar contenedores.

La migración se planificó como 11 tareas TDD bite-sized, se ejecutó con
revisiones por subagentes entre tarea y tarea, y se validó end-to-end con
`docker compose` levantando los 5 servicios (db, MinIO, Redis, API, worker)
y forzando un escenario real de recuperación de huérfanos. Sin cambios en
frontend, sin cambios en BD, sin cambios en la API pública.

## 1. Cierre del frontend web (mañana)

### Lo que se hizo

**Badge de estado de lote unificado** (`BatchStateBadge.vue`): cubre los siete
estados (`created`, `running`, `read`, `transferring`, `transferred`,
`error_*`, fallback) con etiquetas en castellano y `animate-pulse` en los dos
estados activos. Reemplaza tres copias casi idénticas en `BatchListView`,
`DashboardView` y `ApplicationDetailView`.

**Manejo UX de 404 cross-tenant** (issue #39): helper `utils/handleNotFound.ts`
con firma `(err, {router, toast, fallback, message}) → boolean`. Aplicado en
`WorkbenchView` y `ApplicationDetailView` envolviendo el primer `store.fetchOne`.
Cuando un usuario llega por URL a un recurso de otro tenant, en lugar de ver
una pantalla en blanco con un error críptico se le redirige al listado con
un toast "este lote no existe o no es tuyo".

**Auto-refresh del listado** (composable `useBatchesPolling.ts`): polling
silencioso cada 4 segundos mientras hay al menos un lote en `running` o
`transferring`. Garantías: `setTimeout` recursivo (no se solapa), arranque y
parada reactivos, cleanup en `unmount`, errores silenciados (no toast). El
store se extendió con un flag `silent` opcional para que las refrescos
periódicos no parpadeen el `loading`.

## 2. Migración a ARQ — el bloque grande

### Por qué se ha hecho

La implementación previa enrolaba el pipeline y la transferencia con
`BackgroundTasks` de FastAPI, lo que tenía cuatro problemas reales pensando
en producción:

1. **Estados huérfanos**: si el contenedor del API se reiniciaba en mitad de
   un pipeline, el lote quedaba en `running` para siempre y nadie lo
   limpiaba.
2. **Competencia por threads**: cada pipeline ocupaba un slot del threadpool
   del propio API, así que si llegaban diez lotes simultáneos las peticiones
   normales sufrían.
3. **Sin reintentos**: un fallo transitorio (Redis caído, MinIO hipo,
   excepción de OCR) acababa el lote en error sin posibilidad de reintento.
4. **Timeout falso**: el `ThreadPoolExecutor` interno no mata realmente el
   thread cuando vence el plazo, solo deja de esperarlo.

ARQ resuelve los cuatro: es una cola Redis async-nativa, ligera (~3000
líneas, frente a las ~30000 de Celery), pensada para integrarse con FastAPI,
con timeouts duros que sí matan el job y reintentos configurables. Para el
volumen de carga del proyecto (pipelines de segundos a minutos, no millones
de tareas/s) está sobradamente proporcionada.

### Decisión clave: modo `inline` para preservar los tests

El primer obstáculo era la suite de tests: 203 tests web pasan hoy gracias a
que el TestClient de FastAPI ejecuta los `BackgroundTasks` *síncronamente*
después de devolver la respuesta. Si simplemente se cambiaba a
`await pool.enqueue_job(...)`, todos los tests que verifican el estado final
del lote (`assert state == "read"`) fallarían: el job se iría a Redis (que no
existe en tests) y el aserto se haría antes de que nada se procesara.

La solución es un flag `WebSettings.tasks.inline`:

- En **producción** (`inline=False`) los jobs van a Redis y el worker los
  procesa.
- En **tests** (`inline=True`, valor por defecto en pytest) los jobs se
  ejecutan en el mismo proceso del request mediante `asyncio.to_thread`,
  manteniendo el contrato síncrono que esperaba la suite.

El módulo `web/api/tasks/queue.py` expone una sola función para los routers:
`await enqueue_or_run("run_pipeline_for_batch", batch_id=..., storage=...)`.
Internamente decide qué camino tomar. **Los 203 tests web siguen verdes sin
modificar uno solo**.

### Estructura del trabajo

```
web/api/tasks/
├── queue.py           # enqueue_or_run + pool ARQ + registry inline
├── worker.py          # WorkerSettings + pipeline_job/transfer_job/recovery_job
├── recovery.py        # recover_stuck_batches() — UPDATE bulk
├── pipeline_runner.py  # (existente) ahora también se auto-registra inline
└── transfer_runner.py  # (existente) ahora también se auto-registra inline
```

Los runners actuales (`run_pipeline_for_batch`, `run_transfer_for_batch`)
**no cambian de firma**: siguen siendo síncronos y reciben `(batch_id,
storage, ...)`. Esto era importante para no introducir un refactor
horizontal del pipeline. El handler ARQ async simplemente los invoca con
`asyncio.to_thread(...)` para no bloquear el event loop del worker.

El storage (MinIO o filesystem) **no se serializa por Redis** — el worker
construye su propio singleton en `on_startup` y lo guarda en el `ctx`. Los
handlers lo leen de ahí.

### Validación end-to-end con docker compose

Tras completar las 11 tareas se levantó el stack completo y se ejercitaron
dos escenarios reales:

1. **Arranque limpio**: `docker compose up -d` deja los 5 servicios sanos.
   El API enrola `recovery_job` al arrancar; el worker lo procesa en
   **0.15 segundos**.
2. **Recuperación de huérfano**: marcar manualmente un lote a `running` en
   la BD, reiniciar el API. El worker recibe el nuevo `recovery_job` y
   loguea "Recovery: 1 batches huérfanos marcados error_read". La BD
   confirma el cambio de estado.

Tras la prueba se restauró el lote afectado a su estado previo (`read`).

### Bugs descubiertos durante la validación e2e

- **`arq==0.26.3`** (versión inicial del plan) llamaba a
  `asyncio.get_event_loop()` al construir el `Worker`, lo que en Python
  3.14 lanza `RuntimeError`. La 0.28.0, publicada el 2026-04-16, añade
  soporte explícito a Python 3.14.
- **El worker no cargaba todos los modelos SQLAlchemy** antes de la
  primera consulta. La relación `Application ↔ Template` se referencia
  por nombre y no se podía resolver. Se centralizaron los imports en
  `web/api/_register_models.py` (cargado por `main.py` y por `worker.py`).
- **`pytest-asyncio==0.24.0`** forzaba un downgrade de pytest a 8.x
  (incompatible con la suite). Se subió a 1.3.0, compatible con pytest 9.

## Decisiones tomadas

- **Modo `inline` en `TasksSettings`**: preserva los 203 tests web
  existentes sin modificarlos. La env var
  `DOCSCAN_WEB_TASKS__INLINE=false` activa ARQ en producción.
- **Los runners siguen siendo síncronos**, invocados con `asyncio.to_thread`
  desde el handler async. Reescribirlos a async (psycopg async, opencv
  async, scripts Python async) sería un proyecto aparte sin beneficio
  inmediato.
- **`max_tries=1`** por defecto: un fallo de pipeline no reintenta
  automáticamente. La causa más probable es contenido del lote, no fallo
  transitorio. El operador re-dispara con `/run`.
- **`job_timeout=600s`** (10 minutos): suficiente para lotes con OCR. Si
  vence, ARQ mata el job y el `try/finally` del runner garantiza estado
  terminal.
- **Recovery se enrola desde el lifespan del API**, no del worker: el API
  es el proceso garantizado al arrancar. Si el worker no está vivo
  todavía, el job se queda en cola y se procesa cuando arranque.
- **Side-effect imports consolidados en `_register_models.py`**: tanto el
  API como el worker lo cargan, garantizando que SQLAlchemy resuelve
  todas las relaciones por nombre.
