# Progreso 2026-08-04 — Trabajo desde varios equipos: contexto y herramientas portables

## Resumen

Sesión corta de infraestructura, posterior al cierre de los lotes de FlexibarNET
del 28 de julio. El punto de partida era una petición sencilla —subir el trabajo
para continuarlo desde un PC con Windows— que al verificarla destapó tres
problemas: el contexto acumulado del proyecto no viajaba con el repositorio,
había contraseñas en claro en ese contexto, y las protecciones automáticas de
ficheros sensibles se desactivaban sin avisar en Windows.

No se ha tocado código de la aplicación. Dos commits sobre `main`, ya publicados.

## 1. El contexto del proyecto no viajaba con el repositorio

El histórico que Claude acumula entre sesiones —decisiones ya cerradas, bugs
conocidos, preferencias de trabajo— se guardaba en una carpeta local de cada
máquina, fuera del repositorio. Peor aún, el nombre de esa carpeta se deriva de
la ruta absoluta del proyecto, que en Linux y en Windows es distinta, de modo que
ni copiándola a mano habría encajado.

La consecuencia práctica: al abrir el proyecto en el PC nuevo se habría empezado
de cero, sin saber que existe el bug de migraciones de base de datos, que la
versión web está archivada o que ciertas alternativas ya se descartaron en su
día. Con el riesgo asociado de rehacer trabajo o reabrir discusiones cerradas.

Las 31 entradas pasan a estar versionadas dentro del repositorio, y las
instrucciones del proyecto las señalan como primera lectura de cada sesión.

Conviene tener presente que **esta copia no se actualiza sola**: al cerrar una
sesión en la que se haya modificado el contexto hay que resincronizarla. El
procedimiento queda documentado en el propio repositorio y anotado en la memoria
para que no se olvide.

Commit: **`8d71a14 chore(claude): hace el contexto y el tooling portables entre Linux y Windows`**

## 2. Credenciales en claro camino de un repositorio público

Al volcar ese contexto apareció un problema que no se buscaba: contenía dos
contraseñas en texto plano y un hash bcrypt, correspondientes a la base de datos
de pruebas del proyecto web archivado. El repositorio de DocScan es **público**.

Se han redactado antes de publicar nada, y los valores reales siguen únicamente
en el gestor de contraseñas. Como no basta con arreglarlo una vez —cada
resincronización futura puede volver a arrastrar credenciales—, el procedimiento
documentado incluye ahora un barrido obligatorio antes de cada publicación.

Merece la pena señalar que se trataba de credenciales de un entorno de pruebas
local, no de producción. Aun así, publicarlas habría sido un descuido evitable, y
el patrón de las contraseñas podría coincidir con otras en uso.

## 3. Las protecciones se desactivaban en silencio bajo Windows

El proyecto tiene dos automatismos que se disparan cada vez que se edita un
fichero: uno formatea el código Python y otro **bloquea la edición de ficheros
con credenciales** (`.env`, el almacén cifrado `secrets.enc`).

Ambos dependían de una utilidad, `jq`, que el entorno de línea de comandos de
Windows no incluye. El del formateo simplemente habría dejado de funcionar, lo
cual es molesto pero visible. El de la protección era el problema serio: sin esa
utilidad no fallaba con un error, sino que **dejaba pasar la edición como si todo
estuviera correcto**. Se habría trabajado durante semanas creyendo que los
ficheros de credenciales estaban protegidos cuando no lo estaban.

Se han corregido tres cosas:

- La utilidad pasa a ser opcional; si falta, se extrae la información con
  herramientas presentes en cualquier sistema.
- Las rutas de Windows, que usan la barra invertida, no se reconocían: un fichero
  `C:\proyecto\.env` no se identificaba como protegido.
- El formateador ahora localiza sus herramientas también en la disposición de
  carpetas que usa Windows.

## 4. Configuración de servicios auxiliares

Los servicios auxiliares que Claude usa para consultar ficheros y bases de datos
tenían rutas absolutas de la máquina Linux escritas a mano, y habrían fallado al
arrancar en cualquier otro equipo. Pasan a resolverse solas según dónde esté el
proyecto, manteniendo el comportamiento actual como valor por defecto.

Commits: **`8d71a14`** y **`82899da chore(claude): registra en memoria el mecanismo de sincronización multiequipo`**

## Verificación

Se comprobó en Linux que las protecciones deniegan `.env` (tanto en formato Linux
como Windows) y `secrets.enc`, y que siguen permitiendo las plantillas públicas
`.env.example` y los ficheros de código; que la alternativa sin `jq` extrae
exactamente el mismo resultado; y que el formateador funciona sobre un fichero
real.

**Queda por validar en el propio PC Windows.** El comportamiento descrito es el
que documenta el fabricante, no algo ejecutado allí. Es la primera comprobación
pendiente de la próxima sesión.

## Decisiones tomadas

- **Versionar el contexto dentro del repositorio, con sincronización manual**: la
  alternativa automática exigiría infraestructura adicional para un beneficio
  pequeño en un proyecto de un solo desarrollador. Se asume el paso manual a
  cambio de que el mecanismo sea transparente y auditable en cada publicación.
- **Redactar las credenciales en lugar de excluir esos ficheros**: se conserva la
  información útil sobre el entorno de pruebas y solo desaparece el valor
  sensible.
- **Mantener las protecciones en formato de guion de shell en vez de reescribirlas
  en Python**: funcionan tal cual bajo Git Bash y reescribirlas habría añadido
  riesgo a un componente de seguridad por una ganancia teórica.
- **Conservar las rutas actuales como valores por defecto**: el equipo Linux
  sigue comportándose exactamente igual; Windows solo necesita definir una
  variable.
