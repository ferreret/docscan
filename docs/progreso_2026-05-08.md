## 1. Chequeo de estado y descarte de alternativas al agente

Antes de abrir el hito 8 se ejecutaron los tres tripwires en paralelo
para confirmar que la rama seguía limpia tras la pausa:

| Suite | Resultado | Tiempo |
|---|---|---|
| Desktop | 865 passed | 4m 44s |
| Web backend + ARQ | 333 passed | 4m 03s |
| Agente local | 79 passed | 1.5s |

Se borró un fichero vacío `--db-path` que había quedado en el directorio
raíz (residuo de un sandbox previo).

A continuación, conversación abierta con el jefe sobre si el agente
local FastAPI podía sustituirse por una extensión de Chrome o por
WebUSB. Conclusión técnica:

- **Extensión de Chrome**: no tiene API para hablar con TWAIN, WIA o
  SANE. `chrome.documentScan` existe sólo en ChromeOS. Native Messaging
  obliga a instalar un binario nativo de todas formas, así que extensión
  + native host = más piezas, no menos.
- **WebUSB**: teóricamente posible pero impracticable. Implica
  reimplementar el protocolo USB del fabricante en JavaScript (lo que
  hace SANE, modelo a modelo) y, en Windows, sustituir el driver del
  fabricante por WinUSB rompe que el escáner funcione con cualquier
  otra aplicación del sistema.
- **eSCL/Mopria (escáneres de red)**: éste sí puede prescindir del
  agente, pero cubre una cohorte pequeña. Para el parque típico de
  oficina (TWAIN/SANE) el agente nativo es la única opción viable.

La conversación cerró con un repaso rápido a la **UX del usuario
final**: cuatro puntos de fricción (instalación, pairing, día a día,
errores) y cuatro mitigaciones (instalador con auto-start, deep link de
pairing, detección automática del agente en "Mi estación", mensajes
humanos para errores nativos). Las dos primeras quedan reservadas para
una Sesión D específica de UX/empaquetado tras el MVP funcional.

## 2. Hito 8 — ADF streaming via NDJSON

### Arquitectura elegida

Tres decisiones de diseño cerradas antes de tocar código:

| Cuestión | Elección |
|---|---|
| Cómo paginar el ADF desde `scanner_service` | Refactor aditivo: extraer el bucle interno a `acquire_iter()` (Generator). `acquire()` queda como `list(self.acquire_iter(...))` — contrato externo idéntico, 0 tests rotos. |
| Transporte agente → frontend | `StreamingResponse` con `application/x-ndjson`. Una línea por evento. WS sería overkill; "bloquear y devolver" rompe la UX en ADFs largos. |
| Subida al SaaS | Una página = un POST a `/api/batches/{id}/pages`. Sin acumular: si la página 25 falla, las 24 anteriores ya están en el lote. |

Decisión deliberada adicional: el endpoint **NO chequea
`is_disconnected`**. Si el operario cierra el navegador a media cinta,
el bucle agota el ADF y las páginas siguen subiendo al SaaS. El razonamiento
es que perder páginas físicas que ya pasaron por el rodillo sería peor
UX que un cliente que no ve los últimos eventos. Esta decisión simplifica
muchísimo el endpoint (sync, sin puentes asyncio↔threadpool).

### Refactor del servicio de escáner

`app/services/scanner_service.py` recibe un nuevo método
`BaseScanner.acquire_iter(source, config) -> Iterator[np.ndarray]` con
implementación por defecto que delega en `acquire()` (`yield from`).
`SaneScanner` sobreescribe con la versión generator real: el `while
True` del bucle interno pasa a yield cada `image` en cuanto la lee del
fichero temporal de scanimage, en vez de acumularla en una lista local.

`acquire()` se reescribe en una línea:

```python
def acquire(self, source, config):
    return list(self.acquire_iter(source, config))
```

`TwainScanner` y `WiaScanner` no se tocan. Heredan el default
`yield from self.acquire(...)` que mantiene el contrato pero sin
streaming real (al no haber hardware Windows en la máquina de
desarrollo, no se puede mejorar ni testar; el streaming real en Windows
queda para una iteración futura cuando alguien tenga el hardware).

### Endpoint nuevo

`POST /scan-adf-and-upload` en `docscan_local_agent/routers/scan_adf.py`.
Body:

```json
{ "scanner_name": "...", "batch_id": 42, "resolution": 300, "mode": "Color" }
```

Respuesta: stream `application/x-ndjson` con cuatro tipos de evento:

```
{"event":"started"}
{"event":"page_uploaded","page_index":0,"page_id":100,"batch_page_count":1}
{"event":"page_uploaded","page_index":1,"page_id":101,"batch_page_count":2}
{"event":"completed","total":2}
```

Si algo falla a media iteración, en vez de `completed` se emite una
línea `error` con un código semántico (`scan_error`, `upload_error`,
`saas_unavailable`, `encode_error`) y el stream se cierra. Errores
*previos* al stream (401 sin pairing, 404 scanner desconocido, 503 sin
backends) devuelven el código HTTP real, sin NDJSON.

## 3. Hito 9 — Vista "Mi estación" con detección y pairing

### Decisiones de diseño

- **CORS amplio en el agente, sin credentials**. El frontend en el
  origen del SaaS (`https://docscan.example.com` en producción,
  `http://localhost:5173` en dev) tiene que poder hablar con
  `http://127.0.0.1:47816`. Se añade `CORSMiddleware` con
  `allow_origins=["*"]` y `allow_credentials=False`. La auth interna del
  agente es por presencia de `agent.json` en disco (no cookies), así que
  cerrar credentials anula el riesgo de CSRF desde una web maliciosa
  autenticada en el SaaS contra el agente del operario.
- **Hito 9 NO incluye los botones "Escanear"**. La captura sube al SaaS
  contra un `batch_id` concreto, y el `batch_id` sólo existe cuando el
  operario está dentro de un lote (workbench). Por eso los botones
  flatbed/ADF se integran en el workbench en el hito 10, no en "Mi
  estación". La vista de hoy sólo expone detección + pairing + lista de
  escáneres en read-only.
- **`agent_token` nunca pasa por el frontend**. Lo persiste el agente en
  `~/.docscan/agent.json` con permisos 0600 y se usa internamente como
  `Authorization: Bearer ...` cuando el agente sube páginas al SaaS.

### Store Pinia `agent.ts`

Nuevo store en `web/frontend/src/stores/agent.ts` con tres acciones:

- `detect()` — GET `127.0.0.1:47816/status`. En cualquier error de red
  marca `available=false` (el agente no está instalado o está caído).
- `pair(deviceName)` — encadena tres pasos: (1) `api.post('/agent/pair-init', {name})`
  contra el SaaS para reservar el `AgentDevice` y obtener el código de 8
  caracteres, (2) `fetch POST 127.0.0.1:47816/pair` con
  `{saas_url: window.location.origin, code}` para que el agente canjee y
  persista, (3) `detect()` para refrescar el estado.
- `loadScanners()` — GET `127.0.0.1:47816/scanners`. Si devuelve 503
  (sin backends) deja `scanners=[]` y un mensaje legible.

La diferenciación entre llamadas al SaaS (`api.post`) y llamadas al
agente (`fetch` directo a `127.0.0.1:47816`) es explícita: dos
origenes distintos, dos transports distintos. El agent_token nunca
cruza el navegador.

### Vista `MiEstacionView.vue`

Tres estados visuales en una sola vista, controlados por
`agentStore.available` y `agentStore.paired`:

1. **Sin agente detectado**: tarjeta con icono y mensaje "No detectamos
   el agente local". Texto explicando qué es y un placeholder
   *Instaladores Windows / Linux disponibles próximamente* (la descarga
   real llega con la Sesión D de empaquetado PyInstaller).
2. **Detectado sin vincular**: tarjeta amarilla con un input para el
   nombre del equipo ("Portátil mostrador", "PC sala 2") y un botón
   *Vincular este equipo* que ejecuta el `pair()` encadenado. Cero
   copy-paste de códigos por parte del operario.
3. **Vinculado**: tarjeta verde con `device_name`, `user_email` y
   `tenant_name` en grid de tres columnas, más un panel con la lista de
   escáneres. Si la lista está vacía muestra un mensaje sugiriendo
   conectar uno y pulsar *Comprobar de nuevo*.

Entrada en el sidebar entre *Lotes* y *Equipo*, accesible para todos
los roles (no sólo `company_admin`). Ruta `/mi-estacion` con guard
`auth:true`.

## Decisiones tomadas

- **Refactor aditivo en `scanner_service`**: `acquire_iter` con default
  que delega en `acquire`. Motivación: el tripwire desktop no puede
  romperse, así que cualquier subclase que no tenga implementación real
  de streaming (Twain, Wia) sigue funcionando con el default.
- **NDJSON sobre WebSocket o SSE**: NDJSON es estándar HTTP plano, fácil
  de consumir desde `fetch().body.getReader()` y no requiere
  infraestructura adicional en el agente. WS sería overkill (no hay
  canal de vuelta) y SSE añade ceremonia (`text/event-stream`,
  reconnect handshake) que no necesitamos.
- **Sin cancelación por desconexión**: explicada arriba. Las páginas
  capturadas se conservan; la cancelación explícita (con un endpoint
  separado o un flag) queda como follow-up.
- **TwainScanner/WiaScanner sin streaming real**: aceptado para el MVP.
  Cuando alguien tenga hardware Windows con ADF, sobreescribirá el
  `acquire_iter` real. Mientras tanto el contrato se cumple aunque sea
  bloqueante.
