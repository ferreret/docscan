# Progreso 2026-08-05 — Puesta en marcha en Windows y un fallo que borraba datos

## Resumen

Continuación directa de la sesión del 4 de agosto, cuyo primer punto pendiente
era precisamente validar el arranque de la aplicación en el PC con Windows. El
objetivo era modesto —actualizar el repositorio y comprobar que arranca— pero al
ejecutarlo aparecieron tres problemas, uno de ellos serio: **las migraciones de
base de datos borraban los datos del usuario en silencio**.

La aplicación quedó funcionando y verificada visualmente en Windows. Un commit
sobre `main`, ya publicado.

## 1. La aplicación no se podía instalar en Windows

El equipo tenía las dependencias de marzo, muy por detrás del repositorio. Al
actualizarlas, la instalación abortaba entera por una sola línea: la versión
fijada de `pywin32`, una biblioteca necesaria para hablar con Windows, no existe
para la versión de Python que usa el proyecto. No es que fallara esa biblioteca y
el resto siguiera: el instalador se detiene y **no instala nada**.

El detalle relevante es por qué no se había detectado antes. Esa dependencia solo
se instala en Windows, y las comprobaciones automáticas del proyecto se ejecutan
en Linux, donde la línea sencillamente se ignora. Era invisible hasta que alguien
intentara instalar en Windows por primera vez, que es lo que ocurrió hoy.

Corregido subiendo a la versión inmediatamente posterior, que es la que ya estaba
en uso en el equipo y funciona.

## 2. Migrar la base de datos destruía lotes, páginas y códigos de barras

Este es el hallazgo importante de la sesión.

La base de datos del PC databa de marzo y necesitaba actualizarse al esquema
actual. Antes de tocar la original se probó la actualización **sobre una copia**,
por precaución. El resultado:

| | Antes | Después |
|---|---|---|
| Lotes | 8 | 0 |
| Páginas | 42 | 0 |
| Códigos de barras | 58 | 0 |

La aplicación quedaba operativa, pero vacía. Sin ningún mensaje de error.

La causa es una particularidad de SQLite, el motor de base de datos que usa la
versión de escritorio. Ciertos cambios de estructura no se pueden hacer
directamente: hay que crear una tabla nueva, copiar los datos, **borrar la
original** y renombrar. Ese borrado intermedio, combinado con la regla que
mantiene la coherencia entre tablas —si desaparece una aplicación, desaparecen
sus lotes—, arrastraba en cascada todo el contenido asociado. La documentación
oficial de la herramienta de migraciones advierte de esto y exige desactivar esa
regla mientras dura la operación; el proyecto nunca lo hacía.

El alcance conviene dejarlo claro: desde la versión 0.1.5 la aplicación migra la
base de datos **sola al arrancar**. Cualquier instalación con una base de datos
anterior a abril habría perdido su contenido la primera vez que se abriera, sin
posibilidad de recuperarlo salvo copia de seguridad. Las versiones 0.1.5 y 0.1.6
publicadas contienen el fallo.

Se ha corregido desactivando esa regla durante las migraciones y volviéndola a
activar al terminar, incluso si la migración falla a mitad. Verificado sobre la
base de datos real: los 8 lotes, 42 páginas y 58 códigos sobreviven, la
coherencia entre tablas queda intacta y la protección vuelve a estar activa al
acabar.

## 3. Los tests leían y sobrescribían la configuración real del usuario

Al pasar la batería de pruebas apareció un fallo que no correspondía a ninguna
regresión: un test daba por hecho que el origen de documentos empieza en
«Importar», pero en este equipo estaba guardado «Escáner» de una sesión de marzo
con el Canon DR-M160.

El problema de fondo no era el test sino que **las pruebas trabajaban sobre la
configuración real de la aplicación** en el equipo: la leían, dependían de ella y
además la sobrescribían al ejecutarse. Es decir, pasar los tests modificaba las
preferencias del usuario.

Se han aislado en una ubicación temporal desechable. La configuración real quedó
intacta, comprobado tras el cambio.

Commit: **`82eeeb4 fix: las migraciones ya no borran datos en SQLite + entorno Windows`**

## Verificación

A diferencia de la sesión anterior, esta vez la comprobación **sí se hizo en el
propio equipo Windows**:

- La aplicación arranca, migra la base de datos y muestra el lanzador con la
  aplicación «Test Windows». Verificado visualmente sobre captura de pantalla:
  tema oscuro, barra lateral, buscador y selector de idioma correctos.
- Estuvo abierta unos cincuenta minutos con uso real —incluido cambio de tema
  claro/oscuro— y cerró limpiamente, sin errores.
- Batería completa de pruebas en verde y revisión de estilo sin observaciones.
- Copia de seguridad de la base de datos conservada en el equipo antes de migrar.

**Sigue sin probarse el escáner físico.** Es lo único que no se puede verificar
sin el hardware delante y queda como comprobación pendiente.

## Decisiones tomadas

- **No tratar el fallo de migraciones como urgente**: no hay ninguna instalación
  en producción, así que nadie está expuesto hoy. La corrección se aplica igual
  porque ya estaba hecha y no cuesta nada mantenerla, pero no justifica una
  versión correctiva inmediata.
- **Probar la migración sobre una copia antes que sobre la base de datos real**:
  fue precisamente lo que permitió detectar la pérdida de datos antes de causarla.
  Conviene que sea el procedimiento por defecto ante cualquier salto de esquema
  con datos que importen.
- **Aislar la configuración en los tests en lugar de ajustar el test que fallaba**:
  el síntoma era un test, el problema era que toda la batería tocaba
  configuración real. Corregir solo el síntoma habría dejado el resto igual.
- **Subir la dependencia en vez de bajar la versión de Python**: la cadena se
  unificó en Python 3.14 en julio por buenas razones; revertirlo por una
  biblioteca auxiliar habría sido desproporcionado.
