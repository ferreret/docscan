# Progreso 2026-04-07 — Inicio versión web SaaS

## Resumen

Sesión dedicada a la revisión del plan de la versión web SaaS de DocScan Studio, decisiones arquitectónicas y primera implementación funcional de la API REST con FastAPI.

## 1. Revisión y rediseño del plan web

Se realizó una revisión exhaustiva del plan original (27-03-2026) que proponía **FastAPI + Vue 3 + Supabase + Celery + Redis + PostgreSQL**. Tras analizar el código existente y evaluar cada componente, se simplificó el stack:

### Cambios respecto al plan original

| Componente | Plan original | Decisión final | Motivo |
|---|---|---|---|
| Auth | Supabase Auth | **JWT custom (python-jose + bcrypt)** | Control total para multi-tenancy B2B |
| Storage | No especificado | **MinIO (Docker, gratuito)** | API S3-compatible, sin vendor lock-in |
| Task queue | Celery + Redis | **ARQ + Redis** | Más ligero para pipeline síncrono |
| Database | Supabase (PostgreSQL) | **PostgreSQL directo (asyncpg)** | Sin dependencia de terceros |
| Escáner | Agente local básico | **docscan_worker + mini FastAPI** | Reutiliza código existente |
| Despliegue | No especificado | **Docker Compose con overrides** | On-premise y cloud desde mismo código |

### Hallazgos clave de la revisión

- **85% del código Python es reutilizable** sin cambios (pipeline, servicios, providers, modelos, repositorios)
- El **PipelineExecutor funciona como unidad atómica** — una tarea de background simplemente envuelve `execute(page, batch, app)`, no hay que distribuir pasos individuales
- **Supabase eliminado** por vendor lock-in innecesario
- **Celery reemplazado por ARQ** — sobredimensionado para pipeline síncrono
- **Sandboxing de scripts** identificado como problema crítico no contemplado en el plan original (multi-tenant + `exec()` = riesgo de seguridad)

### Modos de despliegue

Se diseñó la arquitectura para soportar **dos modos** desde el mismo código:

- **On-premise**: servidor en casa del cliente, transferencias directas a red local
- **Cloud/SaaS**: servidor en la nube, transferencias locales delegadas al agente

## 2. Implementación: API REST funcional

### Estructura creada

```
web/
  api/
    config.py              — WebSettings (DB, JWT, MinIO, Redis, deploy_mode)
    database.py            — Engine PostgreSQL + SessionDep + reset_engine()
    main.py                — FastAPI app factory con lifespan, CORS
    models.py              — Tenant + User + constantes de roles
    auth/
      security.py          — bcrypt hash + JWT create/decode
      dependencies.py      — CurrentUser, require_role(), OAuth2 scheme
      router.py            — /register, /login, /token, /me
    routers/
      health.py            — GET /health
      applications.py      — CRUD completo tenant-scoped
    schemas/
      auth.py              — TokenResponse, LoginRequest, RegisterRequest, UserResponse
      application.py       — ApplicationCreate/Update/Response/ListItem
    tasks/                 — Preparado para tareas de pipeline (futuro)
```

### Endpoints implementados

| Método | Ruta | Descripción | Auth |
|---|---|---|---|
| GET | `/health` | Health check | No |
| POST | `/api/auth/register` | Crear tenant + usuario admin | No |
| POST | `/api/auth/login` | Login JSON → JWT | No |
| POST | `/api/auth/token` | Login form-data (Swagger) | No |
| GET | `/api/auth/me` | Perfil del usuario autenticado | JWT |
| GET | `/api/applications` | Listar aplicaciones del tenant | JWT |
| POST | `/api/applications` | Crear aplicación | JWT |
| GET | `/api/applications/{id}` | Detalle de aplicación | JWT |
| PATCH | `/api/applications/{id}` | Actualizar aplicación | JWT |
| DELETE | `/api/applications/{id}` | Eliminar aplicación + lotes | JWT |

### Multi-tenancy

- Campo `tenant_id` nullable añadido a `Application` y `Batch` (no rompe desktop)
- Migración Alembic generada y aplicada
- Todos los endpoints filtran por `tenant_id` del usuario autenticado
- **Test de aislamiento**: tenant A no puede ver ni modificar datos de tenant B

### Refactoring del código existente

- **Dataclasses extraídas** de `recognition_worker.py` a `app/pipeline/page_context.py` (PageContext, BatchContext, AppContext, BarcodeResult, PageFlags) — ahora compartidas entre desktop, web y CLI
- **BarcodeResult deduplicado**: `barcode_service.py` ahora importa desde `page_context.py` en vez de definir su propia copia
- **Re-exports** en `recognition_worker.py` para mantener compatibilidad con todos los imports existentes

### Revisiones de seguridad y calidad (2 rondas /simplify)

- **Timing attack corregido**: verificar `user.active` antes de `verify_password` en login
- **Constantes de roles**: `ROLE_SUPERADMIN`, `ROLE_COMPANY_ADMIN`, `ROLE_OPERATOR` (antes strings sueltos)
- **Lifespan fail-fast**: la API no arranca si no puede conectar a la BD (antes silenciaba el error)
- **`reset_engine()`**: limpieza correcta de singletons al cerrar
- **Bug fix**: `tenant_id` podría ser sobreescrito por `**model_dump()` — reordenado
- **Bug fix**: renombrar aplicación a string vacío saltaba validación de unicidad
- **Schema base class**: `_ApplicationBase` elimina ~30 líneas de campos repetidos
- **Dead code eliminado**: `TokenPayload` no usado, `db=None` engañoso
