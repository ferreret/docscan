# Progreso 2026-04-15 — Sesión de prueba manual del MVP web y fixes derivados

## Resumen

Sesión en la rama `feature/web` dedicada por completo a **validar manualmente
el MVP web** antes de seguir añadiendo funcionalidad (envío de invitaciones por
email, etc.). Se levantó el stack completo en Docker (Postgres + MinIO + Redis
+ API + frontend Vite), se preparó una guía de prueba estructurada y una
bitácora, y se ejecutaron los escenarios con Playwright pilotado por el
asistente para los flujos funcionales. El ejercicio destapó **tres bugs reales
y dos limitaciones funcionales**; los tres bugs quedan **corregidos** en esta
sesión. El suite de tests se mantiene verde (**948 passing**, 97 web tras
añadir el test de regresión del fix de password).

## 2. Bugs de entorno encontrados al levantar el stack

### 2.1 Migración no portable SQLite → Postgres

La migración `4a90ab536830_add_pipeline_processed_to_pages.py` usaba
`server_default=sa.text('0')` sobre una columna `Boolean`. SQLite lo acepta
(internamente los bool son integers), pero **Postgres es estricto** y el
despliegue limpio reventaba con `DatatypeMismatch: column "pipeline_processed"
is of type boolean but default expression is of type integer`. Los tests de
migración añadidos ayer no lo detectaron porque también corren sobre SQLite.

Fix: `sa.text('0')` → `sa.false()`, que renderiza `0` en SQLite y `FALSE` en
Postgres. Deuda técnica asumida: añadir a futuro un job CI que corra
migraciones contra Postgres — hoy solo se validan contra SQLite, y este tipo
de divergencia puede repetirse.

### 2.2 CORS fijo a `localhost:5173`

El puerto 5173 de Vite estaba ocupado por otro proyecto del usuario, así que
se arrancó el frontend en 5180. El CORS de la API solo permitía 5173 por
defecto. Solución puntual: inyectar `DOCSCAN_WEB_CORS_ORIGINS` con ambos
orígenes desde `docker-compose.yml`.

## 3. Bugs del producto detectados y corregidos

### 3.1 Errores de validación de pydantic en UI como JSON crudo

Al intentar registrarse con un email `.local` (rechazado por `EmailStr`), el
frontend pintaba la respuesta 422 literalmente:

```
[ { "type": "value_error", "loc": [ "body", "email" ], "msg": "...", ... } ]
```

Causa: `client.ts` hacía `body.detail || 'Error desconocido'`, y cuando
`detail` era un array de errores de pydantic el `||` lo dejaba pasar tal cual
al mensaje.

Fix: añadida función `formatDetail` en `web/frontend/src/api/client.ts` que
detecta si `detail` es array y formatea como `campo: mensaje · campo: mensaje`.

### 3.2 401 en login enmascarando el error de credenciales

Síntoma: al meter una contraseña mal, **"no pasaba nada"** — ni mensaje, ni
spinner, ni error. En logs la API devolvía 401 correctamente, pero el
frontend se recargaba a `/login` al instante y borraba la caja de error.

Causa: `client.ts` redirigía *cualquier* 401 a `/login`, sin distinguir entre
"tu sesión expiró" y "tus credenciales son incorrectas en el propio login".

Fix: el redirect solo dispara si había un `access_token` en localStorage
(sesión preexistente). Si todavía no estás autenticado, el 401 burbujea al
formulario y se muestra "Credenciales incorrectas".

### 3.3 Registro aceptaba contraseñas de 3 caracteres

El caso más grave. `RegisterRequest.password: str` sin ninguna validación de
longitud. Se pudo registrar un usuario con password `123`. Inconsistencia
clara: `AcceptInvitationRequest` **sí** tenía `Field(min_length=8)`.

Fix:
- Backend: `web/api/schemas/auth.py` — `password: str = Field(min_length=8)`,
  además de `min_length=1` en `display_name` y `tenant_name` (evitan cadenas
  vacías).
- Frontend: `RegisterView.vue` — `minlength="8"` en el input y label
  "Mínimo 8 caracteres".
- Test de regresión nuevo: `test_registro_password_corta_422` en
  `tests/test_web_api.py` verifica que `password="1234567"` devuelve 422.

Bajo este cambio, 15 tests existentes que usaban passwords cortas (`"p"`,
`"pass"`, `"pass123"`) rompieron y han sido actualizados a passwords válidas.

### Tests

- Actualizados ~30 call-sites en `tests/test_web_api.py` a passwords >= 8

- Suite completa: **948 passing**, 0 failures.

## 5. Limitaciones funcionales (no son bugs) destapadas

Estas dos no se tocan hoy, son decisiones de producto:

- **No hay editor de pipeline en el frontend web.** La vista `/applications/:id`
  solo muestra metadatos; el pipeline se sigue editando desde el configurador
  de escritorio. Hay que decidir si se añade al MVP web o se mantiene así.
- **Overlays de barcodes no aparecen** en el visor, consecuencia directa del
  punto anterior: el pipeline por defecto no incluye `BarcodeStep` y desde web
  no se puede configurar.

## Decisiones tomadas

- **Fix de migración en el archivo existente** en lugar de crear una migración
  nueva de "arreglo": la revisión `4a90ab536830` todavía no había corrido en
  ningún entorno Postgres, así que reescribir el archivo es seguro. Si hubiera
  habido despliegues Postgres previos habría tocado otra estrategia.
- **`sa.false()` / `sa.true()`** como patrón estándar para booleanos con
  default en migraciones futuras: renderizan correctamente en cualquier
  dialecto. A documentar.
- **Mismo mensaje "Credenciales incorrectas" para password mal y email
  inexistente**: no se cambia. No revelar si un email está registrado es
  buena práctica estándar.
- **Mantener el link de invitación visible en la UI del admin** (ya estaba
  así, se confirma): hasta que esté el envío por email, permite al admin
  compartir manualmente sin intervención en BD.
- **No añadir rate limiting hoy**: elección de librería y tuning no trivial,
  no bloquea el MVP. Se trata como ítem propio.
