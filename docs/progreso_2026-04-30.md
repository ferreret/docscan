## 1. Smoke test e2e con ARQ — dos bugs descubiertos y arreglados

### Setup del test

`docker compose up -d --build` levantó los 5 servicios sanos (db,
MinIO, Redis, api, worker). Se registró un tenant (`SmokeTest`),
se creó una aplicación con un único **ScriptStep** trivial:

```python
def main(app, batch, page, pipeline):
    page.fields["smoke_ok"] = "yes"
```

Se subieron 2 PNGs de 100×100 al lote y se llamó `POST /api/batches/1/run`.

### Bug 1 — `SerializationError: unable to serialize job "run_pipeline_for_batch"`

El router pasaba el `storage` (un `MinIOStorage` resuelto por DI) como
kwarg a `enqueue_or_run`, y `enqueue_or_run` lo reenviaba a
`pool.enqueue_job(...)`. ARQ intenta serializar todos los argumentos
para meterlos en Redis, y `MinIOStorage` con sus conexiones HTTP no es
pickle-able.

En modo `inline` (tests) la función se invocaba con
`asyncio.to_thread(func, *args, **kwargs)` y todo pasaba — el storage
nunca cruzaba un boundary serializable. El bug solo se materializa con
Redis real.

**Solución**: parámetro keyword-only `inline_kwargs` en
`enqueue_or_run`. Los kwargs ahí dentro se inyectan al runner sólo en
modo inline; en modo ARQ se descartan silenciosamente, porque el
handler del worker los reconstruye desde `ctx` (el `storage` se
construye una vez en `on_startup` y vive en `ctx["storage"]`, justo el
diseño documentado en el plan de migración).

```python
# Antes
await enqueue_or_run("run_pipeline_for_batch",
                    batch_id=batch.id, storage=storage)

# Después
await enqueue_or_run("run_pipeline_for_batch",
                    batch_id=batch.id,
                    inline_kwargs={"storage": storage})
```

### Bug 2 — `function 'run_pipeline_for_batch' not found`

Tras el fix anterior, el job se enrolaba bien pero el worker lo
rechazaba: el router enrolaba un job con nombre
`run_pipeline_for_batch` mientras que el worker registraba la función
con su `__qualname__`, que era `pipeline_job` (el nombre del handler
async). ARQ no encontraba el nombre.

**Solución**: usar `arq.worker.func(handler, name="...")` para alinear
el nombre con el que enrola el router. Las funciones internas siguen
llamándose `pipeline_job` y `transfer_job` por claridad de código; el
runner síncrono se importa con alias (`_pipeline_runner`,
`_transfer_runner`) para que no choque con el nombre registrado en ARQ.

```python
class WorkerSettings:
    functions = [
        func(pipeline_job, name="run_pipeline_for_batch"),
        func(transfer_job, name="run_transfer_for_batch"),
        recovery_job,
    ]
```

## 2. Bug #37 — log del workbench mostraba "?" en vez del número

El `LogPanel` del workbench mostraba `Pipeline iniciado (? páginas)` y
`Página N/?` durante la ejecución, en vez del total real. Causa: el
backend emite `total_pages` (en `pipeline_started`) y `total` (en
`page_processed`), pero el composable `useWorkbenchLog.ts` leía
`ev.page_count` — un nombre que el backend nunca ha emitido.

Los **tests usaban los mismos nombres incorrectos**, por eso no se
detectó. Ajustados para reflejar el contrato real.

Suite frontend tras el cambio: **391 passing**, 0 fallos.

Commit: **`74eb088 fix(web-frontend): log pipeline_started/page_processed
lee total_pages/total`**.

## Decisiones tomadas

- **`inline_kwargs` como kwarg explícito en lugar de filtrar por
  introspección**: es más legible para quien lee el router (queda
  visible que `storage` solo aplica en inline) y no introduce magia
  basada en tipos no-serializables. La separación inline vs ARQ es
  intencional, no accidental.

- **Mantener nombres de funciones Python (`pipeline_job`,
  `transfer_job`) y registrar con alias en ARQ**: en lugar de renombrar
  los handlers a `run_pipeline_for_batch`, lo cual chocaría con el
  nombre del runner síncrono. El uso de `arq.worker.func(name=...)`
  desacopla "nombre lógico de la cola" de "nombre Python de la
  función".

- **El bug #37 también requería tocar tests**, no solo código: los
  tests acompañaron la implementación errónea con los mismos nombres.
  Aprendizaje: en bugs descubiertos manualmente, antes de corregir el
  código revisar siempre si los tests están midiendo el contrato real
  o uno inventado.

## 5. Auditoría WS events frontend ↔ backend (4 hallazgos)

Tras descubrir el bug #37 se hizo una pasada sistemática por todos los
`emit()` del backend (`pipeline_runner.py`, `transfer_runner.py`,
`ws.py::broadcast_page_updated`) comparándolos con los consumers del
frontend (`useWorkbenchWebSocket.ts` y `useWorkbenchLog.ts`). Cuatro
desajustes silenciosos en el log panel, todos arreglados:

1. **`page_error` rama muerta**: el switch del log tenía un case
   para un evento que el backend no emite jamás. Los errores de
   página vienen como `page_processed` con `ok=false, error=...`.
   Ahora `page_processed` se ramifica por `ev.ok` y muestra el
   error como nivel `error` cuando aplica.
2. **`pipeline_completed` leía `ev.elapsed`** (nunca emitido) y
   siempre salía como `info`. Ahora usa `ev.any_error` para
   diferenciar "Pipeline completado" (info) de "Pipeline completado
   con errores" (warn).
3. **`pipeline_error` no se capturaba en el log**: el toast
   aparecía pero el LogPanel no mostraba el motivo
   (`batch_not_found`, `application_not_found`). Añadido como case
   error.
4. **`transfer_aborted` ignoraba `reason`** (`not_configured`,
   `validate_returned_false`). Ahora se incluye en el mensaje.

Mejoras añadidas: `transfer_started` muestra `total_pages` y `mode`,
`transfer_completed` muestra `files_transferred` y se ramifica por
`success` (error si false).

`useWorkbenchWebSocket.ts` ya leía bien todos los campos; no
necesita cambios. Los tests acompañaron los nuevos contratos: +6
casos. Suite frontend: **397 passing** (391 → 397).

Commit: **`a1f8f92 fix(web-frontend): auditoría WS events del log
workbench (4 hallazgos)`**.

## 8. Verificación visual de v0.1.1 — bugs descubiertos y arreglados

El usuario instaló el AppImage Linux v0.1.1 y ejercitó los tres
checks propuestos (versión, catálogo de eventos, `page.id` desde
script lifecycle). Resultados:

- ✅ **Versión 0.1.1** confirmada en menú "Acerca de".
- ✅ **`on_batch_loaded` y `on_page_changed`** aparecen en el
  catálogo de eventos del configurador.
- ❌ **`page.id` desde script lanzaba**
  `on_page_changed() missing 1 required positional argument: 'page'`.

Dos bugs descubiertos durante la verificación, ambos arreglados en
`feature/web` por encima de v0.1.1 (van a v0.1.2):

### Bug 1 — Placeholder estático del editor de Eventos

El `QPlainTextEdit` de la pestaña Eventos del configurador tenía un
`setPlaceholderText` hardcoded a `def on_app_start(app, batch):
pass` y nunca cambiaba al seleccionar otro evento del combo. El
usuario veía siempre la firma de `on_app_start` aunque hubiera
elegido `on_page_changed` u `on_key_event`, induciendo a errores
como copiar la firma incorrecta.

Fix:
- Añadidas firmas faltantes a `EVENT_SIGNATURES` para los dos
  eventos promocionados en v0.1.1: `on_batch_loaded(app, batch)` y
  `on_page_changed(app, batch, page)`.
- `tab_events.py` importa `EVENT_SIGNATURES` y nuevo helper
  `_placeholder_for(event_name)` que devuelve el esqueleto correcto
  para el evento seleccionado. Llamado en `_load_from_app` y en
  `_on_event_changed`.

Tests: +2 de regresión. Commit: **`85540eb`**.

### Bug 2 — `on_page_changed` no recibía el objeto `page`

La promesa de v0.1.1 ("page.id accesible desde scripts lifecycle")
solo funcionaba en web. En desktop el dispatcher
(`workbench_window._fire_event` desde `_navigate_to`) pasaba sólo
`page_index=N` (un int) a `on_page_changed`. Un script con la
firma documentada en `EVENT_SIGNATURES` (`def on_page_changed(app,
batch, page):`) fallaba con `missing 1 required positional
argument: 'page'`.

Fix:
- Nuevo helper `_build_page_context(page_index)` análogo al de
  web: lee la página por `(batch_id, page_index)`, materializa
  barcodes y fields, devuelve un `PageContext` con `id`,
  `page_index`, `barcodes`, `ocr_text`, `fields`, `flags`. Robusto
  ante batch ausente o page_index inválido.
- `_navigate_to`: el `_fire_event("on_page_changed", ...)` ahora
  pasa `page=self._build_page_context(page_index)` además de
  `page_index=page_index`. ScriptEngine filtra por signature, así
  que firmas antiguas con sólo `(app, batch)` o `(app, batch,
  page_index)` siguen funcionando — el nuevo `page` se descarta si
  la función no lo declara.
- Restaurado import `APP_DATA_DIR` con `# noqa: F401` (parcheado
  por tests). Mismo bug del hook ruff que en `worker_main.py` el
  2026-04-28: lo borraba al reformatear, rompiendo los tests que
  lo parchean dinámicamente.

Tests: +4 de regresión en `TestBuildPageContextDesktop`. Commit:
**`f852e35`**.
