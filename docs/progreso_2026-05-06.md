## 1. Demo del sprint superadmin y bug arreglado en caliente

Bootstrap del primer superadmin con `python -m web.api.bootstrap
superadmin --email superadmin@tecnomedia.es --password Tecno2026!`.
Login en navegador → guard redirige a `/admin/tenants` con sidebar
"Administración" y listado de los tenants existentes con stats. Se
creó un tenant nuevo `Demo Cliente S.L.` con admin `Ana García` para
verificar el flujo. La vista de detalle (`/admin/tenants/6`) renderiza
cabecera, stats agregadas, datos editables y la lista de usuarios.

Al pulsar Suspender en la cabecera, la vista crasheó con
`Cannot read properties of undefined (reading 'length')` en
`TenantDetailView.vue:284`. Causa-raíz: el endpoint
`PATCH /api/admin/tenants/{id}` declara `response_model=TenantListItem`
(sin `users[]`); sólo el GET incluye usuarios. El store hacía
`currentTenant.value = tenant` con la respuesta del PATCH, dejando
`tenant.users` undefined.

El fix alinea el patrón con `updateUser`/`createUser`/`deleteUser` que
ya hacían `fetchTenant(id)` tras la mutación. Se actualizó el test
existente para mockear PATCH→GET de forma realista (antes el mock
incluía `users[]` y enmascaraba el bug) y se añadió un test de
regresión "no refresca si id no coincide". 461/461 tests frontend
verde.

Se demostraron también el resto de capacidades del sprint superadmin:

- Suspender un tenant → su admin recibe `401 "Tenant suspendido"` al
  intentar login (banner rojo en UI).
- Login como `company_admin` redirige a la home de operador, no a
  `/admin`. El navegador a `/admin/tenants` por URL manual lo
  redirige el guard. La API responde `403 "Rol requerido: superadmin"`
  aunque se intente con un token válido de `company_admin` —
  defense-in-depth confirmado.
- AuditLog registra cada acción con actor, target y payload del
  cambio.

Tras la demo se limpió la BD entera: solo TecnoMedia + superadmin.
También se purgaron los 2 PNGs huérfanos del bucket MinIO.

Commit: **`97dd7f4 fix(web/frontend): admin store refresca tenant tras PATCH para no perder users[]`**

## 2. Sprint de documentación MkDocs

Auditoría inicial reveló que `mkdocs.yml`, `docs-web/` y la URL
pública estaban congelados desde el 2026-03-26 — entre medias se
construyó toda la web SaaS (217 commits) y se publicaron las versiones

no había workflow CI: el deploy era manual con
`mkdocs gh-deploy` y dependía de que alguien se acordase.

Sprint de talla M+ con cuatro entregables:

### Workflow CI nuevo `.github/workflows/docs.yml`

Dispara en push a `main` que toque `docs-web/`, `mkdocs.yml` o
`requirements-docs.txt`, y también manualmente desde la pestaña
Actions. Hace `mkdocs build --strict` (falla si hay enlaces rotos o
warnings) y deploy a la rama `gh-pages` con
`mkdocs gh-deploy --force --no-history`.

`requirements-docs.txt` fija las versiones (`mkdocs==1.6.1`,
`mkdocs-material==9.7.6`, `mkdocs-material-extensions==1.3.1`) para
builds reproducibles entre máquina local y CI.

### Sección "Versión Web SaaS" — 5 páginas nuevas

Reorganización de `mkdocs.yml` con dos secciones top-level: "Versión
Desktop" (con la doc previa intacta) y "Versión Web". Cada página de
la nueva sección sin capturas (pendientes hasta que la UI esté
estable, según preferencia del jefe):

- `docs-web/web/index.md` — visión general, diferencias clave con
  desktop, cuándo elegir cada una, diagrama ASCII de los componentes
  del despliegue.
- `docs-web/web/getting-started.md` — login, registro, conceptos
  multi-tenant (tenant, user, roles superadmin/company_admin/operator),
  caducidad de sesión, bloqueo por tenant suspendido.
- `docs-web/web/workbench.md` — diferencias respecto al desktop
  (sin escáner aún, procesamiento en servidor, multi-usuario), 16

- `docs-web/web/admin.md` — admin de empresa, superadmin, bootstrap
  CLI, gestión de tenants, AuditLog y defense-in-depth.
- `docs-web/web/deploy.md` — Docker Compose, variables de entorno,
  servicios (api, worker ARQ, db, redis, minio), bootstrap del
  primer superadmin, recovery automático, troubleshooting. Refunde
  el contenido obsoleto de `docs/deploy.md` (que ahora es solo un
  puntero a esta nueva ubicación).

### Parche menor del manual desktop

### Hito 3 — Endpoints `/api/agent/*`

Cuatro endpoints nuevos en `web/api/routers/agent.py`:

| Método | Ruta | Auth | Descripción |
|---|---|---|---|
| POST | `/api/agent/pair-init` | Bearer JWT user | Genera código de 8 chars, crea AgentDevice pre-pairing |
| POST | `/api/agent/pair-claim` | (público) | El agente reclama el código y obtiene su `agent_token` |
| GET | `/api/agent/whoami` | Bearer agent_token | Info del dispositivo + user + tenant propietarios |
| POST | `/api/agent/heartbeat` | Bearer agent_token | Actualiza `last_seen` |

Diseño clave del token de agente: formato `{device_id}.{secret_hex}`.
El prefijo permite buscar el AgentDevice en BD por id en O(1) y
verificar bcrypt sólo del secret. Sin prefijo tendríamos que comparar
bcrypt contra todas las filas — O(N) prohibitivo a escala.

Nueva dependency `get_current_agent` en `web/api/auth/dependencies.py`
que valida el header Bearer como agent_token (parsea formato, busca
device, verifica bcrypt, comprueba tenant activo). NO acepta JWT de
usuario — un token JWT no tiene formato `{id}.{secret}` y falla con
401. El sprint reservará una dependency híbrida para el Hito 7
(cuando el endpoint de upload de páginas tenga que aceptar ambos).

Schemas en `web/api/schemas/agent.py` con Pydantic: `PairInitRequest`,
`PairInitResponse`, `PairClaimRequest`, `PairClaimResponse`,
`AgentInfo` (con `AgentUserInfo` + `AgentTenantInfo` anidados),
`HeartbeatResponse`.

14 tests TDD bite-sized en `tests/test_web_agent.py`:

- pair-init: genera código de 8 chars, requiere JWT de usuario, persiste
  device pre-pairing en BD.
- pair-claim: 404 código inválido, 410 expirado, 404 doble uso (porque
  el código se nullea tras el claim), 200 con token correcto.
- whoami: 401 sin token, JWT user no vale, 401 token con formato
  inválido, 200 con info completa user+tenant.
- heartbeat: 200 actualiza `last_seen`, 401 sin token / token inválido.

Commit: **`060e1e9 feat(web): hito 3 — endpoints /api/agent/* (pairing + heartbeat)`**

## Decisiones tomadas

- **Cloud-first para el sprint del cliente local web**: el SaaS está
  pensado como pieza de portfolio del usuario, alojada por él. El
  agente local debe resolver el caso "servidor remoto que no ve la
  red del cliente" (descargar páginas para transferencia local), no
  sólo subir.
- **Token de agente con prefijo `{id}.`**: hacerlo opaco habría
  obligado a O(N) en bcrypt. Con el prefijo la verificación es O(1)
  por consulta directa por id + un solo bcrypt verify del secret.
- **Tests del agente separados del repo principal**: viven en
  `docscan_local_agent/tests/` porque el agente es un paquete
  autocontenido destinado a empaquetarse con PyInstaller. Los
  tripwires del repo principal (`pytest tests/`) no los incluyen.
- **No meter capturas de la web en el manual MkDocs ahora**: la
  interfaz aún cambiará. Texto + diagramas ASCII bastan; las
  capturas vendrán cuando la UI se estabilice.
- **Sin capturas, talla M de doc en una sola sesión**: bajó de 4-5h
  estimadas a ~3h reales. Bloquear el sprint por capturas pulidas
  habría sido perfeccionismo.
