## 1. Demo del sprint superadmin y bug arreglado en caliente

Bootstrap del primer superadmin con `python -m web.api.bootstrap
superadmin --email superadmin@tecnomedia.es --password Tecno2026!`.
Login en navegador → guard redirige a `/admin/tenants` con sidebar

verificar el flujo. La vista de detalle (`/admin/tenants/6`) renderiza
cabecera, stats agregadas, datos editables y la lista de usuarios.

Al pulsar Suspender en la cabecera, la vista crasheó con
`Cannot read properties of undefined (reading 'length')` en
`TenantDetailView.vue:284`. Causa-raíz: el endpoint
`PATCH /api/admin/tenants/{id}` declara `response_model=TenantListItem`
(sin `users[]`); sólo el GET incluye usuarios. El store hacía
`currentTenant.value = tenant` con la respuesta del PATCH, dejando
`tenant.users` undefined.

El fix alinea el patrón con `updateUser`/`createUser`/`deleteUser` que
ya hacían `fetchTenant(id)` tras la mutación. Se actualizó el test
existente para mockear PATCH→GET de forma realista (antes el mock
incluía `users[]` y enmascaraba el bug) y se añadió un test de
regresión "no refresca si id no coincide". 461/461 tests frontend
verde.

Se demostraron también el resto de capacidades del sprint superadmin:

- Suspender un tenant → su admin recibe `401 "Tenant suspendido"` al
  intentar login (banner rojo en UI).
- Login como `company_admin` redirige a la home de operador, no a
  `/admin`. El navegador a `/admin/tenants` por URL manual lo
  redirige el guard. La API responde `403 "Rol requerido: superadmin"`
  aunque se intente con un token válido de `company_admin` —
  defense-in-depth confirmado.
- AuditLog registra cada acción con actor, target y payload del
  cambio.

Tras la demo se limpió la BD entera: solo TecnoMedia + superadmin.
También se purgaron los 2 PNGs huérfanos del bucket MinIO.

### Hito 3 — Endpoints `/api/agent/*`

Cuatro endpoints nuevos en `web/api/routers/agent.py`:

| Método | Ruta | Auth | Descripción |
|---|---|---|---|
| POST | `/api/agent/pair-init` | Bearer JWT user | Genera código de 8 chars, crea AgentDevice pre-pairing |
| POST | `/api/agent/pair-claim` | (público) | El agente reclama el código y obtiene su `agent_token` |
| GET | `/api/agent/whoami` | Bearer agent_token | Info del dispositivo + user + tenant propietarios |
| POST | `/api/agent/heartbeat` | Bearer agent_token | Actualiza `last_seen` |

Diseño clave del token de agente: formato `{device_id}.{secret_hex}`.
El prefijo permite buscar el AgentDevice en BD por id en O(1) y
verificar bcrypt sólo del secret. Sin prefijo tendríamos que comparar
bcrypt contra todas las filas — O(N) prohibitivo a escala.

Nueva dependency `get_current_agent` en `web/api/auth/dependencies.py`
que valida el header Bearer como agent_token (parsea formato, busca
device, verifica bcrypt, comprueba tenant activo). NO acepta JWT de
usuario — un token JWT no tiene formato `{id}.{secret}` y falla con
401. El sprint reservará una dependency híbrida para el Hito 7
(cuando el endpoint de upload de páginas tenga que aceptar ambos).

Schemas en `web/api/schemas/agent.py` con Pydantic: `PairInitRequest`,
`PairInitResponse`, `PairClaimRequest`, `PairClaimResponse`,
`AgentInfo` (con `AgentUserInfo` + `AgentTenantInfo` anidados),
`HeartbeatResponse`.

14 tests TDD bite-sized en `tests/test_web_agent.py`:

- pair-init: genera código de 8 chars, requiere JWT de usuario, persiste
  device pre-pairing en BD.
- pair-claim: 404 código inválido, 410 expirado, 404 doble uso (porque
  el código se nullea tras el claim), 200 con token correcto.
- whoami: 401 sin token, JWT user no vale, 401 token con formato
  inválido, 200 con info completa user+tenant.
- heartbeat: 200 actualiza `last_seen`, 401 sin token / token inválido.

## 5. Sprint cliente local web — Sesión B (hitos 4-7)

### Hito 4 — Pairing en el agente

`POST /pair` en el agente cierra el flujo de auth: el usuario pega el
código que vio en la web y el agente lo canjea contra el SaaS,
persistiendo las credenciales en `~/.docscan/agent.json` con permisos
`0600` (sólo el dueño del proceso).

Diseño del módulo `credentials.py`:

- `AgentCredentials` Pydantic: `saas_url`, `agent_token`, `device_id`,
  `device_name`, `user_email`, `tenant_name`, `paired_at`.
- Escritura **atómica** (`tmp + os.replace`) — un fallo a media
  escritura no deja el JSON corrupto.
- Permisos `0o600` aplicados al fichero final (sólo POSIX; en Windows
  el ACL del directorio del usuario ya restringe).
- `load_credentials()` devuelve `None` si el fichero no existe, está
  corrupto o no cumple el schema (no crashea el agente).

`saas_client.py` evolucionó: nuevos métodos `pair_claim` y `whoami`
con httpx síncrono inyectable. Errores tipados (`PairClaimError`,
`WhoamiError`, `SaasUnavailable`) que el router relayea al frontend
con su `status_code` original. Importante: el agente NO depende de
`web.api.*` — replica los schemas en `saas_schemas.py` (réplicas
mínimas de `AgentInfo`/`AgentUserInfo`/`AgentTenantInfo`) para no
arrastrar SQLAlchemy/alembic al PyInstaller del agente.

Endpoint `POST /pair`:

- Body: `{saas_url, code}`. El `device_name` lo recibe el SaaS desde
  pair-init (lo puso el usuario en la web), no se duplica aquí.
- Si ya hay credenciales → 409 sin tocar el SaaS.
- Errores del SaaS relayed con su status: 404 código no válido, 410
  expirado, 502 si SaaS unavailable.
- **Nunca devuelve el agent_token al cliente** — sólo metadatos
  descriptivos (`device_name`, `user_email`, `tenant_name`).

`GET /status` pasa a leer las credenciales reales y devuelve
`paired: true` con metadatos cuando hay agent.json válido. El frontend
del SaaS lo usa para detectar si el agente está vivo y vinculado antes
de mostrar la UI de pairing o el panel "Mi estación".

Tests TDD bite-sized: **+31** (10 credentials + 8 saas_client + 9 pair
+ 4 status nuevos). Total agente: **34**.

Smoke e2e contra stack docker (tras rebuild + migración alembic):
pair-init → /pair → agent.json escrito (0600, token con prefijo
`{device_id}.`) → /status `paired:true` con metadatos del whoami →

### Hito 7 — Cierre Sesión B: agente sube páginas al SaaS

El hito más complejo de la sesión porque toca dos paquetes (SaaS +
agente) y cierra la cadena auth+pair+scan+upload end-to-end.

**Cambios en el SaaS** (`web/api/auth/dependencies.py`):

Nueva clase `Principal` (frozen dataclass) + `get_current_user_or_agent`.
Acepta un Bearer token en el header y prueba dos paths:

1. **JWT user** (decodifica con la clave del SaaS). Si OK, resuelve a
   un `User` con tenant activo.
2. **Agent_token** (formato `{device_id}.{secret}`). Si JWT decode
   falla y el token tiene `.`, busca el `AgentDevice` por id, verifica
   bcrypt del secret, comprueba tenant activo y device no desactivado.

Devuelve un `Principal` unificado con `tenant_id` (siempre),
`user_id` (en agente: el dueño del device), `is_agent` (flag) y
`agent_device_id` (sólo si is_agent).

`upload_pages` en `routers/pages.py` cambia `CurrentUser` →
`CurrentUserOrAgent`. Aislamiento multi-tenant intacto:
`get_batch_for_tenant(principal.tenant_id)` hace 404 si el batch no
es del tenant — un agent_token contra batch ajeno **no leakea**
existencia.

**Cambios en el agente**:

- `SaasClient.upload_page(batch_id, agent_token, png_bytes, filename)`
  con multipart. Excepción `UploadError` paralela a las otras.
- `routers/scan_upload.py` con `POST /scan-and-upload` que encadena
  `require_paired → list_sources → acquire → encode PNG → upload`.
  Errores del SaaS relayed (404 batch ajeno, 401 token revocado),
  502 si SaaS unavailable. El `agent_token` lo lee del agent.json,
  no se acepta en el body.

**Decisión arquitectónica**: el agente sube **directamente** al SaaS
en lugar de devolver el PNG al navegador para que éste lo reenvíe.
Razón: para ADF de N páginas, el doble salto navegador→agente→
navegador→SaaS es prohibitivo. El agente, página a página, sube
directamente. Esto requiere la dependency híbrida (de ahí el orden
de hitos 7 ↔ 8).

Tests TDD: **+13** en SaaS (9 hybrid auth + 4 upload con agent_token),
**+16** en agente (5 upload_page client + 11 scan-and-upload).
Totales: web **333**, agente **79**.

Smoke e2e contra stack docker (tras rebuild + migración):

| Caso | Resultado |
|---|---|
| Upload con `agent_token` al batch propio | **201 Created** ✅ |
| `GET /batches/X/pages` lista la página subida vía agent_token | ✅ |
| Upload con `agent_token` a `batch_id=9999` (ajeno o inexistente) | **404** ✅ |

**Bug interesante encontrado y documentado**: con `from __future__
import annotations`, las anotaciones de los handlers FastAPI son
strings y FastAPI las resuelve con `get_type_hints()`. Si el alias
`CurrentUserOrAgent` se importa **dentro** de un fixture (no a nivel
módulo), `get_type_hints` no lo encuentra y FastAPI trata el
parámetro como query param → 422 "Field required" en lugar de 401.
Adicional: rutas añadidas tras `TestClient.__enter__()` también
pierden parte de la resolución. Fix: import a nivel módulo + montar
endpoints dummy en fixture pre-TestClient.

## Decisiones tomadas

- **Cloud-first para el sprint del cliente local web**: el SaaS está
  pensado como pieza de portfolio del usuario, alojada por él. El
  agente local debe resolver el caso "servidor remoto que no ve la
  red del cliente" (descargar páginas para transferencia local), no
  sólo subir.
- **Token de agente con prefijo `{id}.`**: hacerlo opaco habría
  obligado a O(N) en bcrypt. Con el prefijo la verificación es O(1)
  por consulta directa por id + un solo bcrypt verify del secret.
- **Tests del agente separados del repo principal**: viven en
  `docscan_local_agent/tests/` porque el agente es un paquete
  autocontenido destinado a empaquetarse con PyInstaller. Los
  tripwires del repo principal (`pytest tests/`) no los incluyen.
- **No meter capturas de la web en el manual MkDocs ahora**: la
  interfaz aún cambiará. Texto + diagramas ASCII bastan; las
  capturas vendrán cuando la UI se estabilice.
- **Sin capturas, talla M de doc en una sola sesión**: bajó de 4-5h
  estimadas a ~3h reales. Bloquear el sprint por capturas pulidas
  habría sido perfeccionismo.
- **Réplica de schemas en el agente** (`saas_schemas.py`): el agente
  NO importa `web.api.schemas.*` para no arrastrar SQLAlchemy/alembic
  al PyInstaller. La duplicación es mínima (3 dataclasses Pydantic) y
  el smoke e2e detectará drift de schema antes de producción.
- **PNG raw en `/scan` (no base64)**: 33% menos de overhead. El
  frontend lo trata como `Blob` estándar.
- **Agente sube directamente al SaaS** en `/scan-and-upload` (no
  doble salto navegador→agente→navegador→SaaS). Esta decisión exigió
  la dependency híbrida user+agent y es la razón del orden hitos 7
  ↔ 8: necesitamos auth aceptando agent_token antes de poder
  streamear desde ADF.
- **Lazy import de `app.services.scanner_service`** en la factory:
  el agente arranca aunque falten SANE/TWAIN. Sólo `/scanners` falla
  con 503 si no hay backend. `/status` y `/pair` siguen disponibles.
