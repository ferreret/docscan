# Progreso 2026-04-20 — Editor de pipeline v2 (ImageOpStep)

## Resumen

Sesión dedicada íntegramente al **sub-proyecto 2 del configurador web**: el
editor de pipeline para pasos de tipo *ImageOp* (operaciones de imagen).
Continuación natural del editor v1 de *BarcodeStep* cerrado el 17 de abril.
Rama `feature/web`. 16 commits, cero cambios en el backend: las 24
operaciones ya estaban implementadas en `app/services/image_pipeline.py` y
sólo había que exponerlas en la web con UX tipado.

## 1. Diseño y plan aprobados

Antes de tocar código se celebró una sesión de *brainstorming* completa
sobre tres decisiones de alcance:

- **Catálogo completo de las 24 operaciones** desde la primera versión web
  (no un subset curado). El desktop ya las soporta y la web debía
  equipararse sin asteriscos.
- **Metadata del catálogo en frontend**, no en backend. Un fichero TS con
  24 entradas es más manejable que añadir dataclasses por op o servir un
  endpoint de schema; la desviación con el backend se detecta en un test
  de paridad.
- **Selector agrupado** por categoría (Geometría, Color, Limpieza,
  Morfología, Canales, Efectos) en un `<optgroup>` nativo. Sin modal ni
  buscador — suficientes 6 grupos para 24 entradas.

También se decidió dejar **fuera de scope** cualquier preview del
resultado (requiere endpoint nuevo y componente dedicado, tratable como
sub-proyecto separado si se demanda más adelante) y mantener el campo
`window` como 4 inputs numéricos tipados en lugar de un selector visual.

Commit: **`79bc791 docs(superpowers): spec y plan del editor de pipeline v2 (ImageOpStep)`**.

## 2. Implementación TDD por capas

El plan se ejecutó con subagentes en tareas bite-sized, cada una con
tests escritos antes del código. 13 tareas, cada una con su commit
individual:

### Capa 1 — Tipos y catálogo

- **Tipo `ImageOpStep`** añadido al dominio TS. Modela exactamente el
  dataclass del backend (`op: string`, `params: Record<string, unknown>`,
  `window: [number, number, number, number] | null`).
- **Catálogo TS** con las 24 operaciones del backend: nombre, etiqueta
  ES, categoría, descripción y lista de campos con tipo, default y
  rangos. Un test de paridad verifica que las 24 claves coinciden con
  `IMAGE_OPS` del backend.

Commits: **`e557ce2`, `15ac09a`**.

### Capa 2 — Widgets genéricos de formulario

Cinco widgets reutilizables más uno específico para el ROI, cada uno
fully-controlled (recibe `modelValue`, emite `update:modelValue`):

| Widget | Función |
| --- | --- |
| `NumberField` | Input numérico con clamp a min/max y modo entero. |
| `EnumField` | Select que preserva el tipo (number/string) del value. |
| `BooleanField` | Checkbox + label. |
| `PointField` | Dos `NumberField` (X, Y) que emiten `{x, y}`. Reservado para uso futuro. |
| `ColorField` | Tres `NumberField` (R, G, B 0-255) + swatch en vivo. |
| `WindowField` | Toggle "Aplicar solo a una región" + 4 inputs (X, Y, W, H) o `null`. |

Cada widget llegó con su suite vitest. Total 22 tests nuevos de esta
capa.

Commits: **`9be110f, dcb6ba6, 3cdfc47, 72f3da2, ca6e84c, fe1ded2`**.

### Capa 3 — El ensamblador `ImageOpStepForm`

El componente principal lee el catálogo y monta los widgets
dinámicamente según la op elegida. Incluye un caso especial para
**`Resize`**: los parámetros `scale` y `(width, height)` son mutuamente
excluyentes y se modelan con un `EnumField` "Modo" cuyo valor se
**infiere** de los params actuales (si hay `width` y `height`, modo
`size`; en otro caso, `scale`) — sin estado local que pueda
desincronizarse.

Entre las decisiones relevantes:

- Al cambiar de operación, `params` se reemplaza con los defaults del
  nuevo schema; `window` se conserva (es transversal a la op).
- Con `op: ''` solo se muestra el selector; el botón Guardar del drawer
  queda deshabilitado hasta que el usuario elija una operación.

Siete tests vitest cubren todos los flujos: op vacío, cambio de op,
Rotate (enum), FxGrayscale (sin campos), Resize en ambos modos.

Commits: **`05561d6, a8596d8, 3311308`**.

### Capa 4 — Integración con el resto del editor

- **Menú "Añadir step"**: la opción *Operación de imagen* pasa de
  "Próximamente" a activa con badge v2; OCR y Script siguen
  deshabilitados (sub-proyectos 3 y 4 pendientes).
- **Drawer**: rama `image_op` en el `<switch>` de formularios; lógica
  del botón Guardar consolidada en un único `canSave` computed que
  cubre validez y la regla específica `op !== ''` para image_op.
- **Fila del pipeline**: resumen compacto como
  `"Convertir a 1 bit · threshold=180 · región 0,0,100,100"`, usando
  la etiqueta ES del catálogo en vez del nombre técnico.

Commits: **`c535030, 68f7997, 0bfe5f1`**.

### Documentación interna

- `PointField` quedó sin uso en producción (ninguna op del catálogo
  tiene `type: 'point'` — `FloodFill` modela x/y como dos campos `int`
  separados). Se añadió un comentario explicando por qué existe el
  widget y cómo adoptarlo en el futuro, para evitar confusión en
  contribuciones posteriores.

Commit: **`4b77b21`**.

### Tests

**36 tests nuevos** sobre los 8 originales del editor v1 = **44/44
passing** en la suite frontend, cero regresiones. Sin tests nuevos en
backend (la API `PUT /api/applications/{id}/pipeline` ya cubre
`ImageOpStep` desde v1).

## 3. Validación end-to-end en navegador real

Tras cerrar los 16 commits se arrancó el stack local (Postgres + API +
dev-server de Vite) y se validó todo el flujo con Playwright contra un
usuario real:

1. **Login** con `demo2@demo.com` en la aplicación "Pipeline Test v1"
   (app id 8).
2. **Selector**: el menú muestra "Operación de imagen v2" activo junto
   a Barcode v1; las 24 operaciones aparecen agrupadas en 6 categorías
   dentro del `<select>`.
3. **Creación**: se crearon tres pasos — `ConvertTo1Bpp` con umbral 180
   y región custom (0,0,100,100), `Resize` cambiando el modo a *Tamaño
   (px)* con 1200×800, y `AutoDeskew` sin parámetros.
4. **Persistencia**: inspección directa de `pipeline_json` en Postgres
   confirmó que:
   - `ConvertTo1Bpp` guarda `{"threshold": 180}` y `window` como tupla
     de 4 enteros.
   - `Resize` guarda solo `{"width": 1200, "height": 800}` — sin
     `scale`, lo que demuestra que el cambio de modo limpia los
     parámetros del modo anterior.
   - `AutoDeskew` guarda `{"params": {}, "window": null}`.
5. **Round-trip**: al recargar la página, los 4 pasos se reconstruyen
   con el resumen correcto y la reedición de `Resize` abre el drawer
   directamente en modo *Tamaño (px)* — el `resizeMode` inferido
   funciona.

## Decisiones tomadas

- **Catálogo completo desde v2**: en lugar de entregar un subset curado
  y dejar el resto para una v2.1, se cubren las 24 ops de golpe. Las
  opciones sin parámetros (AutoDeskew, FxGrayscale, etc.) son
  triviales; las complejas comparten widgets.
- **Schema en frontend, no en backend**: evita tocar 24 funciones
  Python o introducir un endpoint nuevo. A cambio se asume la disciplina
  de actualizar el catálogo cuando se añada una op al backend — un test
  de paridad lo detecta.
- **Sin preview de resultado**: un preview requiere endpoint nuevo,
  upload, componente dedicado y una decisión sobre almacenamiento
  efímero. Se trata como sub-proyecto aparte si se demanda.
- **`Resize` con modo inferido, no estado local**: el tipo de
  redimensionado (escala vs tamaño absoluto) se deriva puramente de los
  params presentes. Así el componente permanece *fully-controlled* y no
  puede quedar desincronizado.
- **Consolidación de `canSave`**: tras la revisión de calidad, la
  lógica del botón Guardar se unificó en un único computed que cubre
  validez y reglas específicas por tipo, en vez de combinar `!valid`
  con `!canSave` en el template.
