# Progreso 2026-04-21 (v5) — Pestaña Eventos web con on_scan_complete

## Resumen

Tercera tanda del día tras cerrar por la mañana la verificación desktop
(`progreso_2026-04-21.md`) y por la tarde el sub-proyecto 4 del
configurador web (`progreso_2026-04-21_v5.md` corresponde a este

extrajo un componente `<CodeEditor>` genérico reutilizable a partir

solo evento (`on_scan_complete`) que sí ejecuta el backend web. 17
commits en `feature/web`.

## 1. Diseño y plan aprobados

Brainstorm que exploró cómo encajar una segunda vista que usa
CodeMirror. Decisiones clave:

- **Extraer `<CodeEditor>` ahora** que hay dos consumidores
  (ScriptStep + Eventos) en lugar de duplicar código.
- **Navegación por tabs** (Resumen | Pipeline | Eventos) en un
  `<AppHeader>` compartido, preparando el terreno para futuras
  pestañas (Imagen, Campos, Transferencia, General).
- **Contexto adaptado por evento** en el catálogo frontend.
- **Sidebar + editor central** con dirty tracking, save/undo y guard
  de navegación.

## 3. Giro de scope: reducir a on_scan_complete

Durante el final review se detectó un problema arquitectónico real: el
backend web (`web/api/tasks/pipeline_runner.py`) **solo ejecuta los
ScriptStep del pipeline**. Los 13 eventos del catálogo que se iban a
mostrar al usuario nunca se dispararían en web — el runtime que los
ejecuta es exclusivamente el Workbench desktop. Mostrar 13 eventos
editables sin ejecución confundiría al usuario.

El usuario validó la preocupación y pidió el enfoque honesto: **solo
mostrar los eventos que el web ejecuta**. Con ese criterio
`on_scan_complete` es el único con semántica idéntica al desktop en
web hoy. El resto esperan a su UI correspondiente:

| Evento | Cuándo añadir |
| --- | --- |
| `on_transfer_validate`, `on_transfer_advanced`, `on_transfer_page` | Cuando llegue pestaña Transferencia en web. |
| `on_navigate_*`, `on_key_event` | Cuando exista visor programable en web. |
| `on_app_start`, `on_app_end` | Pendiente de definir cuándo tienen sentido (no hay Workbench persistente en web). |
| `init_global`, `verification_panel` | Nunca: desktop exclusivos (launcher / QWidget). |

Cuatro tasks adicionales cerraron el giro:

- **`d457f01 refactor(web-frontend): reducir events-catalog a solo on_scan_complete`**.
  Catálogo reducido a 1 entrada. Se eliminan `PAGE_VAR`, `RESULT_VAR`,
  `KEY_VAR`, `VERIFICATION_PANEL_VARS` y helper `tpl()` — sin eventos
  que los consuman.
- **`ea6a935 test(web-frontend): ajustar EventsEditorView al catálogo reducido`**.
  8 tests adaptados: sidebar con 1 item, referencias a
  `on_scan_complete` en lugar de `on_app_start`/`on_app_end`.
- **`486efdd feat(web-api): disparar on_scan_complete tras pipeline`**.
  Helper `_fire_scan_complete(application, app_ctx, batch_ctx)` en el
  runner backend. Parsea `events_json`, compila el script con
  `ScriptEngine`, lo ejecuta con `app` y `batch` como kwargs. Errores
  logueados como warning sin abortar el flujo. El batch context que
  recibe el script refleja el estado final (`state="read"`). 7 tests
  backend nuevos (total 967/967 passing).
- **`6487263 docs(superpowers): revisión de scope del sub-proyecto Eventos`**.
  Spec y plan anotados con la decisión de scope y la tabla de eventos
  pospuestos.

## 4. Simplificaciones `/simplify`

Tras cerrar la implementación se pasó un `/simplify` con 3 agentes en
paralelo (reuse, quality, efficiency). 8 fixes aplicados en un único
commit:

- **`5032332 chore: simplificaciones tras review /simplify en sub-proyecto Eventos`**.
  - `BASE_VARS` ahora deriva de `CONTEXT_VARIABLES.filter(...)` en
    `events-catalog.ts`, eliminando duplicación de 10 líneas.
  - `AppHeader` extrae los 3 `router-link` a un `v-for` sobre tabs
    computadas.
  - `CodeEditor.disabled` prop muerta eliminada; mocks de tests
    actualizados.
  - `EventsEditorView.onEditorChange` consolidado (2 early-returns
    idénticos → 1); module-level `fetchedForId` eliminado (Pinia ya
    dedupe `fetchOne`).
  - `_fire_scan_complete`: 4 try/except → 2 con
    `ScriptCompilationError` específico + `engine.shutdown()` en
    `finally` (fix de leak de ThreadPoolExecutor).
  - `_build_executor` devuelve `(executor, engine)`; el caller hace
    `shutdown()` en `finally` — fix del mismo leak para el engine
    del pipeline principal.
  - Comentarios WHAT redundantes limpiados en
    `PipelineEditorView.vue` y `pipeline_runner.py`.

## Decisiones tomadas

- **Extraer `<CodeEditor>` al haber 2 consumidores**: decisión correcta
  — `ScriptStepForm.vue` pasó de ~240 a ~70 líneas, `EventsEditorView`
  reutiliza todo el andamiaje sin duplicar código.
- **Scope honesto vs. paridad con desktop**: se decidió mostrar
  solo lo ejecutable en web. Alternativa descartada (mostrar los 13
  con "edit-only" para algunos) habría confundido al usuario.
- **`on_import` fuera del scope de esta iteración**: su semántica
  desktop ("reemplaza la carga estándar") no aplica en web (el upload
  no es sustituible). Podría añadirse en el futuro solo como
  notificación pero cambiaría el contrato vs. desktop. Diferido.
- **`verification_panel` nunca en web**: QWidget, incompatible con el
  navegador. Requeriría re-definir el contrato como plugin Vue con API
  HTTP — sub-proyecto aparte si aparece demanda.
