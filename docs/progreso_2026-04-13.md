# Progreso 2026-04-13 — Frontend pulido + tiempo real + visor + export + equipo

## Resumen

Sesión larga sobre la rama `feature/web`, completando todos los puntos
pendientes del plan web (`project_web_session_next.md`). Cinco ejes: restyling
del frontend alineado con la estética del desktop, WebSocket de progreso del
pipeline en tiempo real, visor de documentos con zoom/pan y overlays de
barcodes, export de lotes como ZIP con manifest, y gestión completa de equipo
(usuarios + invitaciones con token). Todo verificado end-to-end con Playwright
contra la API real y PostgreSQL. El suite de tests web ha pasado de **71 a 92
tests** durante la jornada.

## 1. Restyling del frontend con la paleta del desktop

El frontend Vue 3 usaba una paleta gris/azul genérica de Tailwind que no
compartía lenguaje visual con el desktop. Se han extraído los tokens del
`resources/styles/light.qss` (paleta **Catppuccin Latte**: base `#eff1f5`,
texto `#4c4f69`, primario `#1e66f5`, peligro `#d20f39`, éxito `#40a02b`,
warning `#df8e1d`) y se han declarado como variables `@theme` de Tailwind 4 en
`web/frontend/src/style.css`. Esto genera utilities `bg-base`, `text-subtext`,
`border-surface-0`, etc. que se han propagado por sidebar, auth (login +
register), dashboard, listas/detalle de aplicaciones y lotes.

De propina, durante la verificación visual se detectó un fallo multi-tenant:
la constraint `UNIQUE` sobre `applications.name` era **global**, impidiendo
que dos inquilinos tuviesen aplicaciones con el mismo nombre. Se ha corregido
a `UNIQUE (tenant_id, name)` con la migración Alembic `e5b7c3d94f10`.

Commit: **`106076d feat: restyling frontend web con paleta desktop + fix unique app name por tenant`**

## 2. WebSocket de progreso del pipeline en tiempo real

Hasta ahora el frontend, al lanzar un pipeline, hacía un `setTimeout(3000)` y
refrescaba a ciegas. Se ha sustituido por un canal WebSocket real que emite
eventos de progreso.

La parte delicada era puentear dos mundos: el runner del pipeline corre como
`BackgroundTask` de FastAPI (síncrono, en threadpool) y los consumidores son
corrutinas WebSocket del event loop principal. Para ello se ha creado
`web/api/events.py` con un `PipelineEventBus` singleton que captura el loop en
el `lifespan` de FastAPI y usa `loop.call_soon_threadsafe(...)` al publicar
desde threads. Los suscriptores reciben los eventos vía `asyncio.Queue` por
`batch_id`.

### Endpoints y eventos

| Método | Ruta | Descripción |
|---|---|---|
| `WS` | `/ws/batches/{id}?token=JWT` | Stream de eventos del pipeline para un lote; cierra con 1008 si token inválido o cross-tenant |

Eventos emitidos: `pipeline_started` (con `total_pages`), `page_processed`
(con `processed/total/ok/error`), `pipeline_completed` (con `state/any_error`),
`pipeline_error`.

En el frontend, `BatchDetailView` abre el WS al pulsar "Ejecutar pipeline",
muestra "Procesando N/M…" en el propio botón y refresca el lote al recibir
`pipeline_completed`. Se ha añadido también `websockets==16.0` a
`requirements-web.txt` (el uvicorn[standard] no lo arrastró en la versión
fijada) y el proxy `/ws` con `ws: true` en `vite.config.ts`.

### Tests

4 tests nuevos: happy path (recibir started + processed + completed), token
inválido, aislamiento entre tenants, y resiliencia del bus sin event loop
asociado.

Commit: **`1230130 feat: WebSocket de progreso del pipeline en tiempo real`**

## 3. Visor de documentos con zoom, pan y overlays de barcodes

Hasta ahora, al seleccionar una miniatura aparecía un panel lateral pequeño
con metadatos. Se ha reemplazado por un **visor a pantalla casi completa** al
estilo del workbench del desktop.

`web/frontend/src/components/DocumentViewer.vue` implementa:
- Zoom con rueda del ratón anclado al cursor (mantiene estable el punto bajo
  el puntero), con botones **+/−**, **Ajustar** (fit al viewport) y **1:1**.
- Pan arrastrando con botón izquierdo.
- Overlays semitransparentes por barcode con una paleta de 8 colores vivos y
  etiqueta "simbología: valor" encima.
- Carga autenticada reutilizando el patrón de `AuthImage` (Bearer en `fetch` +
  `URL.createObjectURL`).

En `BatchDetailView`, el click en una miniatura abre un modal con toolbar
superior (cerrar con **Esc**, **prev/next** con flechas, eliminar página) y
sidebar derecho con barcodes, campos parseados, OCR y errores de
procesamiento. El `PageResponse` del API ahora incluye la lista de barcodes
con posición y rol para que el visor pueda pintar los overlays.

Commit: **`3a0a4c7 feat: visor de documentos con zoom, pan y overlays de barcodes`**

## 4. Export de lotes como ZIP con manifest

Se ha añadido la posibilidad de **descargar un lote entero como ZIP** para
exportar los resultados del procesamiento.

### Endpoints

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/batches/{id}/export` | Stream `application/zip` con todas las páginas + `manifest.json` |

El ZIP contiene:
- `pages/page_NNNN.{ext}`: imagen original de cada página, nombrada por índice
  para preservar orden.
- `manifest.json`: metadata del lote (id, state, timestamps) y por cada
  página: OCR completo, campos indexados, lista de barcodes con posición y
  rol, flags `needs_review` / `is_blank` / `pipeline_processed`. Todo en
  UTF-8 sin escapar.

En el frontend se ha añadido el botón **"↓ Descargar ZIP"** en el header del
detalle de lote (deshabilitado si el lote está vacío). La descarga se hace
con `fetch` + blob + `<a download>` temporal para poder enviar el Bearer
token en el header (algo que `<a href>` directo no permite).

### Tests

3 tests nuevos: contenido correcto del ZIP (fichero de página + manifest con
campos esperados), aislamiento multi-tenant (404 cross-tenant), lote vacío
devuelve ZIP solo con manifest.

Commit: **`98f1618 feat: export ZIP de lotes con manifest.json`**

## 5. Gestión de equipo: usuarios, roles e invitaciones

El último bloque añade la administración de miembros del tenant: un
`company_admin` puede listar usuarios, cambiar su rol o desactivarlos, y
**invitar nuevos usuarios por token**.

Se ha creado el modelo `Invitation` (`tenant_id`, `email`, `role`, `token`,
`expires_at`, `accepted_at`, `created_by_user_id`) con migración Alembic
`f7c9d2b85a43`. El flujo de invitación es **out-of-band**: el admin crea la
invitación desde la UI y recibe una URL (`/accept-invitation/<token>`) que
copia al portapapeles y envía por su canal habitual (email manual, chat…).
Esto evita el coste de integrar envío de emails en este MVP.

### Endpoints

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/users` | Lista usuarios del tenant (admin) |
| `PATCH` | `/api/users/{id}` | Cambia rol, activo o nombre (admin) |
| `DELETE` | `/api/users/{id}` | Elimina usuario del tenant (admin) |
| `GET` | `/api/invitations` | Lista invitaciones pendientes (admin) |
| `POST` | `/api/invitations` | Crea invitación con token y TTL 7d (admin) |
| `DELETE` | `/api/invitations/{id}` | Revoca invitación (admin) |
| `POST` | `/api/invitations/accept` | **Público**: acepta token y crea usuario |

El endpoint admite solo `operator` y `company_admin` como roles asignables
(nunca `superadmin`). Se bloquean acciones peligrosas: un admin no puede
desactivarse ni eliminarse a sí mismo. La aceptación valida que el token
existe, no ha sido consumido y no ha caducado; emite 404, 409 o 410 según el
caso.

En el frontend:
- `/team` (solo admin) con listado de usuarios (selector de rol inline,
  toggle activo, eliminar), invitaciones pendientes (copy-link y revocar), y
  modal de invitar que muestra la URL resultante.
- `/accept-invitation/:token` público con formulario nombre + password.
- Sidebar: entrada "Equipo" visible solo si `role === 'company_admin'`.

### Tests

14 tests nuevos cubriendo permisos admin-only (operator recibe 403), cambio de
rol/activo, bloqueo de auto-desactivación y auto-eliminación, rol inválido,
aislamiento entre tenants (404 cross-tenant), creación de invitación, email
ya registrado (409), aceptación correcta y posterior login, token inválido,
doble aceptación (409) y caducidad (410).

### Verificación E2E

Probado con Playwright: admin → crea invitación → copia enlace → logout →
abre enlace → completa registro → login como nuevo usuario → ve las mismas
apps y lotes del tenant pero **sin** la entrada "Equipo" en el sidebar.

Commit: **`5c08180 feat: gestion de equipo — usuarios, roles e invitaciones por token`**

## Decisiones tomadas

- **Paleta como design tokens de Tailwind 4** (`@theme`) en lugar de un
  plugin o de reescribir clases: permite seguir usando utilities nativas de
  Tailwind (`bg-primary`, `text-subtext`) sin infraestructura extra y
  manteniendo el markup limpio.
- **Unique compuesto `(tenant_id, name)` en applications**: se aceptó que
  con `tenant_id IS NULL` (usuarios desktop single-instance) no haya
  protección a nivel SQL; la UI del desktop ya valida el unique al crear.
- **Event bus en memoria para WebSocket** en vez de Redis/pubsub: la API
  se despliega como un único worker por ahora, y un bus in-process es
  suficiente. Cuando escalemos horizontalmente habrá que sustituirlo por
  Redis Streams o similar.
- **Invitaciones out-of-band (sin email sending)**: reduce superficie y
  dependencias en el MVP. Se puede añadir `smtp/sendgrid` después si hace
  falta automatizar.
- **Zoom del visor como CSS `transform: translate + scale`** sobre la
  imagen y los overlays en un contenedor común: mantiene overlays alineados
  sin recalcular posiciones manualmente.
- **Bloquear auto-desactivación / auto-eliminación**: elimina una clase de
  errores catastróficos ("el único admin se desactivó a sí mismo") sin
  requerir lógica sofisticada tipo "debe haber ≥1 admin".
