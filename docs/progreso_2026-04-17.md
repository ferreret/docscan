# Progreso 2026-04-17 — Editor de pipeline web v1 (BarcodeStep)

## Resumen

Sesión de implementación completa del **sub-proyecto 1 de 6 del configurador
web**: el editor de pipeline, en su primera iteración que cubre únicamente
`BarcodeStep`. Continuando desde la sesión de planificación del 2026-04-16,
se ejecutó íntegramente el plan v1 (`docs/superpowers/plans/2026-04-16-pipeline-editor-web-v1.md`)
con metodología *subagent-driven* (subagente fresco por tarea + doble revisión
spec/calidad). Rama `feature/web`, 14 commits nuevos, **960 tests backend + 8
tests frontend** todos en verde.

## 1. Backend — endpoints de pipeline

Se añadieron dos endpoints REST bajo `/api/applications/:id/pipeline` para que
el frontend pueda leer y reemplazar el pipeline completo de una aplicación,
delegando la validación fina a la misma función (`deserialize()`) que usa el
runner del pipeline tanto en el desktop como en la web. Esto garantiza una
sola fuente de verdad para el formato.

### Endpoints nuevos

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/api/applications/{id}/pipeline` | Devuelve el pipeline actual de la aplicación (lista de steps) |
| `PUT` | `/api/applications/{id}/pipeline` | Reemplaza el pipeline entero; valida con `deserialize()` y responde 422 si el contenido no es ejecutable |

Ambos comparten un helper `_get_app_or_404` que aplica el filtro
`tenant_id == user.tenant_id`, garantizando el aislamiento multi-tenant.

### Validación de `Literal` en el serializer

Durante la implementación se detectó que los dataclasses de Python **no
validan `Literal` en runtime**, así que un `engine="motor_fantasma"` pasaba
silenciosamente y sólo fallaba al ejecutar el pipeline. Se añadió
`_validate_literals()` al `app/pipeline/serializer.py` para rechazar esos
valores en el mismo punto donde ya se valida el resto del formato. Es una
mejora compartida desktop+web, no rompe ningún test existente.

### Tests

12 tests nuevos en `tests/test_web_api.py` (5 para GET, 7 para PUT) cubriendo
tenant isolation, round-trip, validación de tipo desconocido, validación de
campo `engine` inválido, persistencia directa en `pipeline_json` y lista
vacía. Suite total: **960 passing** (antes 948).

## 2. Frontend — página `/applications/:id/pipeline`

Se creó una página dedicada para editar el pipeline, accesible desde el detalle
de la aplicación con un botón **"Editar pipeline"**. La orquestación mantiene
el pipeline en un store de Pinia; el drawer lateral de edición usa un draft
local con guardia *dirty* al cancelar, y la persistencia se dispara explícita
por acción (guardar step, reordenar, borrar) — no hay auto-save *on change*.

### Arquitectura de componentes

- `PipelineEditorView.vue` — página, orquesta carga, store, drawer y toasts.
- `PipelineStepList.vue` — lista con drag-to-reorder (`vue-draggable-plus`).
- `PipelineStepRow.vue` — fila compacta con badge de tipo, summary y acciones.
- `PipelineStepDrawer.vue` — drawer lateral con draft local y guardia *dirty*.
- `BarcodeStepForm.vue` — formulario *fully-controlled* (emit del step entero
  en cada cambio; validación de regex con `new RegExp()` en vivo).
- `AddStepMenu.vue` — dropdown para elegir tipo; sólo Barcode habilitado en v1.

Los demás tipos (`image_op`, `ocr`, `script`) aparecen como *"Próximamente"*
en el menú y, si existieran por venir del desktop, el drawer muestra un aviso
informativo en lugar de error.

### Store + tests (primera aparición de vitest)

Se introdujo **vitest** en el proyecto (primera vez) con `@vue/test-utils`,
`jsdom` y `@pinia/testing`. Se añadió un `vitest.config.ts` y los scripts
`test` / `test:watch` en `package.json`. El store `usePipelineStore` tiene
**8 tests** cubriendo fetch, save (éxito y error), addStep, updateStep
(hit/miss), removeStep y reorder.

### Pulido tras code review

El review final detectó cuatro puntos menores. Se aplicaron tres en el acto:

- `loading` del store inicializado a `true` para eliminar un flash del
  empty-state mientras la primera petición no ha resuelto.
- `onBeforeRouteLeave` bloquea también si el drawer está abierto (evita
  perder un step recién añadido al navegar).
- `meta: { auth: true }` en la nueva ruta, alineado con el resto del router
  (antes usaba `requiresAuth` por despiste del template).

El cuarto (extraer `_get_app_or_404` a un módulo común) se aplaza a v2.

## 3. Validación manual end-to-end

Todo el flujo se verificó con Playwright sobre el stack real (Postgres local
+ uvicorn + Vite) y usuario de prueba `demo2@demo.com`. Escenarios validados
en el orden real del usuario:

1. Login → Aplicaciones → crear "Pipeline Test v1" (id 8).
2. Botón **"Editar pipeline"** visible en el detalle → abre `/applications/8/pipeline`.
3. Empty state con mensaje correcto y contador "0 steps".
4. Menú `+ Añadir step` con Barcode activo y los otros tres como
   "Próximamente".
5. Añadir step barcode con QRCODE + regex `^DOC-\d+$` + umbral 0.5 → drawer
   cierra, fila aparece con summary `motor1 · página completa · QRCODE`.
6. Añadir segundo step con motor2 → contador "2 steps".
7. Refresco (F5) → los dos steps persisten.
8. `GET` directo a la API confirma persistencia canónica con los campos
   normalizados.
9. Editar → regex `[` → mensaje *"Regex inválida: Unterminated character
   class"* + botón **Guardar step** deshabilitado.
10. Cancelar con cambios → confirm *"¿Descartar cambios?"*.
11. Borrar step → confirm *"¿Eliminar este step 'barcode'?"* → desaparece.
12. Crear segundo usuario (otro tenant, "Other Org") → `GET` y `PUT` del
    pipeline de la app 8 → **404 "Aplicación no encontrada"**.

Se amplió la bitácora (`docs/MANUAL_TEST_WEB_MVP.md`) con una nueva sección
§9 "Editor de pipeline v1" con los 9 bloques de regresión para futuras
sesiones.

## Decisiones tomadas

- **Validación delegada a `deserialize()` en vez de duplicarla en Pydantic**:
  evita mantener dos esquemas del mismo dominio. El backend de la web valida
  por la misma puerta que el runner del pipeline.
- **`_validate_literals` en el serializer (código compartido)**: beneficia
  también al desktop; el coste es una introspección de `typing.get_type_hints`
  por step deserializado, despreciable.
- **Save explícito por step + persist-on-reorder**: evita auto-save constante
  con cada tecla pero garantiza que el drag-and-drop sí persiste sin botón
  de "Guardar todo". El tradeoff coincide con el mental model esperado.
- **Formulario *fully-controlled***: el form no mantiene estado local y emite
  el step completo; el padre (drawer) mantiene el draft. Elimina la clase de
  bugs de doble-watcher que suelen aparecer con `v-model` + `watch` en Vue 3.
- **Fases por tipo de step**: v1 Barcode → v2 ImageOp → v3 OCR → v4 Script,
  cada una con su propio spec+plan al cerrar la anterior. v1 ya permite al
  usuario configurar el caso más común (separadores de documento por código
  de barras).
